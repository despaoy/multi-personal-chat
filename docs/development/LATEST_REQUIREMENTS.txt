1．项目定位

这是一个基于现有 GitHub 项目继续开发和重构的网页角色聊天系统。

项目仓库标识：
despaoy/multi-personal-chat
如果获得仓库访问权限，请核对实际 Git remote、分支、代码和文档，不要仅凭仓库名称推测实现。

系统面向：
- 我自己和熟人。
- 希望创建、导入和使用自定义角色的用户。
- 希望与原作角色聊天、讨论原作或开展假想剧情的用户。
初期服务个人或少量用户，但必须从一开始实现多账号数据隔离。

优先级从高到低：
1. 角色聊天自然，人物表达稳定。
2. 多轮聊天具有连续性。
3. 记忆可以查看、纠正、删除。
4. 假想剧情可以保存、继续和分支。
5. 用户可以创建、导入、分享自定义角色。
原作问答、可展开出处、关系发展和主动互动也属于当前目标。

我优先考虑效果、效率和质量，不希望因为实现难度或开发时间而直接削减功能。当前先完成可运行、可验证的功能和代码基础，再持续优化模型效果；不要求基础开发结束时模型已经达到完美表现。

2．主要用户流程

系统至少支持以下流程：

流程 A：创建角色并开始聊天
1. 用户登录。
2. 输入角色名字、人设和开场白。
3. 保存角色后立即试聊。
4. 随后可以补充示范对话、人物关系、初始场景和参考资料。
5. 也可以通过导入角色设定文件创建角色。
流程 B：持续聊天
1. 用户与角色进行多轮交流。
2. 角色记住当前话题、约定和相关经历。
3. 对明确的长期偏好，系统按记忆规则保存。
4. 用户离开后再打开同一会话，继续原来的进度。
5. 关系随着对话经历发展，但手动设置优先。
流程 C：重新认识或延续关系
1. 新会话默认初识，不自动使用旧关系和私人记忆。
2. 用户也可以选择“延续关系”。
3. 延续时由用户指定一个已有会话作为起点。
4. 用户明确继承范围。
5. 如果新角色设定与旧经历冲突，系统展示冲突并让用户决定如何处理。
流程 D：尝试另一种剧情
1. 用户从一条已有消息创建假想分支。
2. 分支继承截至该消息的对话和当时状态。
3. 用户选择不同的行动，剧情随之发展。
4. 分支可以保存、继续，也可以切回原会话。
5. 各分支的新经历和关系变化互不自动混用。
流程 E：原作问答
1. 用户向角色询问原作问题。
2. 问题涉及的角色、场景或时间线不明确时，先澄清。
3. 系统检索资料并组织回答。
4. 回答保持角色口吻。
5. 用户可以展开实际引用的出处和原文片段。
6. 缺少证据时明确表达不确定，不编造出处。
3．角色表达要求

角色不能只是套上名字的通用助手。

需要保持：
- 符合人物的用词。
- 符合人物的语气。
- 稳定的说话节奏和表达习惯。
- 符合人设的立场和价值判断。
- 随当前关系变化的反应。
- 对既有经历和当前场景的连续理解。
角色可以：
- 表达不同意见。
- 拒绝用户的要求。
- 争论。
- 提出条件。
- 主动追问。
- 接梗。
- 延续旧话题。
- 提起相关经历。
对于原作角色，尽量贴近原作；对于自建角色，遵循创作者设定。

普通聊天中保持人设，不因为用户随口说一句话就自动修改角色底层设定。

在明确的假想分支中，允许用户通过剧情指令调整人物关系、背景或场景。调整只在相应分支生效，不自动影响原角色版本和其他会话。

例如：
普通聊天中：
用户说“你现在必须完全信任我”，角色仍按当前关系回应。

假想分支中：
用户明确设置“我们已经认识十年，是彼此信任的朋友”，
角色可以依据这个前提继续该分支。
4．角色创建与资料导入

角色编辑应同时适合简单使用和深入定制。

基础字段：
- 名字。
- 人设。
- 开场白。
扩展内容：
- 示范对话。
- 人物关系。
- 初始场景。
- 供角色查阅的资料。
- 导入的角色设定文件。
要求：
- 只填写基础字段即可试聊。
- 不强制用户一开始完成复杂配置。
- 资料与设定需要有明确来源和版本。
- 具体兼容的角色文件格式需要形成清单，不能把“支持导入”理解为天然支持所有格式。
5．角色版本与分享

角色设定使用不可变版本。

规则：
- 编辑并发布后产生新版本。
- 已有会话继续绑定原版本。
- 新会话默认使用最新版本。
- 不静默改变正在进行的会话设定。
分享采用独立复制方式：
- 接收方复制角色后可以自己修改。
- 分享包括角色设定和创作者选入的资料。
- 不包含作者私人聊天、关系进度和记忆。
- 作者和接收方的角色副本独立演进。
- 作者发布更新时提示接收方。
- 是否导入更新由接收方决定。
- 不自动覆盖接收方的修改或现有会话。
验收示例：
朋友复制我分享的角色后修改开场白，
我的原角色保持不变。

朋友与角色聊过的私人经历，
不会出现在我的会话中。
6．会话隔离与关系继承

默认新会话从初识开始。

必须区分：
- 角色原有的背景和设定。
- 用户与角色在某次会话中形成的经历。
- 用户主动授权共享的记忆。
- 假想分支中的新增事实。
“延续关系”必须由用户选择来源会话，不能自动从最近会话、所有会话或全局关系池继承。

采用新设定延续旧关系时：
- 可以继承用户选择的旧关系与记忆。
- 必须检查设定冲突。
- 存在冲突时由用户确认。
- 不能静默丢弃旧经历，也不能把互相矛盾的内容同时当成事实。
7．连续性与上下文

聊天连续性由以下信息共同支撑：
信息	用途
最近对话	当前话题、指代、语气与正在进行的交流
分段摘要	较早对话的主要经过
相关原话	找回具体表述和证据
长期记忆	稳定偏好及重要事实
关系状态	双方相处后的变化
场景状态	当前剧情地点、事件和进度


要求：
- 摘要不能凭空增加事实。
- 原始记录和推导结果分开保存。
- 检索命中不代表可以直接使用，仍需验证账号、角色、会话、分支、版本和有效性。
- 历史分支不能自动知道分支起点之后才出现的信息。
- 刷新、断线、重新登录和服务重启后，已保存状态保持一致。
- 长对话不能只依赖把全部历史反复发送给模型。
8．记忆管理

自动保存规则：
- 明确、稳定、没有冲突的长期偏好可以自动保存。
- 含糊信息等待用户确认。
- 与现有记忆冲突的信息等待确认。
- 用户手动纠正优先于模型推断。
例如：
“今天不想喝咖啡”
不能未经确认就变成“这个人平时不喝咖啡”。

“记住，我平时不喝咖啡”
可以作为明确长期偏好保存。
用户可以：
- 查看记住了什么。
- 查看来源和相关原话。
- 纠正记忆。
- 删除记忆。
- 逐条选择某条记忆是否分享给其他角色。
跨角色共享必须明确授权，不能默认所有角色共用私人记忆。

回复正式保存后，再由可靠后台任务提取记忆、关系和摘要。

后台处理必须：
- 可以重试和恢复。
- 不重复产生相同结果。
- 提交时检查当前修订。
- 尊重用户后来的编辑、纠正、撤回和删除。
- 不用过期结果覆盖新状态。
9．关系系统

关系随着对话经历发展，并影响角色对用户的反应。

要求：
- 支持多维关系状态。
- 自动变化有经历依据。
- 用户能够手动设置关系。
- 手动设置不得被后台模型自动覆盖。
- 对手动设置的改变应作为建议，接受后再生效。
- 分支之间独立演进。
- 编辑和撤回后，关系按保留历史重新确定。
具体维度、数值范围、变化速度和展示方式尚需明确设计。提出方案时说明它们如何影响人物行为，不要仅增加没有实际作用的数值。

10．剧情分支与历史结构

用户可以从已有消息创建多个假想分支。

支持：
- 从消息节点分支。
- 保存并继续分支。
- 返回旧节点。
- 重新选择剧情。
- 切换不同分支。
- 返回原会话。
分支继承截至起点的对话和当时关系等适用状态，之后独立发展。

验收示例：
角色说“我准备离开”。

分支一：用户挽留。
分支二：用户告别。

两条分支有不同后续。
关闭网页后，仍能继续任意一条。
原会话没有被另一分支的新经历覆盖。
底层目标：
不可变消息节点
分支路径
状态快照
来源与修订追踪
创建分支记录本身不算完成，还需验证状态隔离与剧情连续性。

11．编辑、撤回和彻底删除

编辑消息：
- 用户可以修改自己发过的消息。
- 替换当前走向。
- 编辑点之后的消息移出当前会话。
- 从修改处继续。
- 重新确定相关关系和记忆。
- 不强制把每次编辑都变成新分支。
撤回：
- 从指定消息开始撤回后续对话。
- 按保留历史重新确定状态。
- 不能只隐藏消息而继续使用它产生的记忆。
另开分支：
- 保留原走向。
- 创建独立的新走向。
彻底删除：
1. 展示关联分支和副本。
2. 用户选择删除范围。
3. 立即禁止相关内容被继续读取。
4. 清理原文、快照和索引。
5. 拒绝旧任务重新写回。
6. 备份恢复时应用删除记录，防止内容复活。
必须区分“移出当前会话”和“所有关联内容彻底删除”。

12．原作问答与引用

先完成一个预设角色的完整原作问答能力。

要求：
- 导入和管理原作、角色参考资料。
- 资料按版本保存。
- 关键词与向量混合检索。
- 候选重排。
- 必要的上下文展开。
- 回查原始资料，验证候选内容。
- 回答保留角色表达方式。
- 正文简洁，出处可展开。
- 保存本次回答实际使用的引用快照。
问题不明确时先确认角色、场景或时间线。

证据不足时：
- 明确表达不确定。
- 不编造原文和出处。
- 不用没有实际支持回答的检索结果装饰引用。
资料更新后：
- 新会话默认最新资料。
- 旧会话由用户选择是否迁移。
- 不静默替换已有会话的资料依据。
首个预设角色及其资料范围需要明确选择，不能未经确认自行认定。

13．主动互动

聊天过程中允许角色主动追问、接梗和提议话题。

用户授权后，聊天之外支持：
- 接续未完成的话题。
- 关心用户提过的考试、面试等事件。
- 分享符合角色个性的虚构日常。
- 用户长时间没有出现后的问候。
控制规则：
- 按会话授权。
- 用户可设置频率。
- 用户可设置免打扰时段。
- 同一事件或任务不能重复发送。
- 撤销授权后，旧任务不能继续发送。
- 虚构日常要留作剧情记录。
- 不把虚构活动描述成系统在现实世界中执行过的操作。
具体默认频率、上限和事件时间识别规则需要设计清楚。

14．消息与通知

支持两种送达方式，由用户选择：
1. 保存在应用内，下次打开网页时看到。
2. 用户授权后发送浏览器通知，同时保存在应用内会话。
应用内消息是正式记录，通知只是提醒。

因此：
- 通知失败不能导致正式消息丢失。
- 通知重试不能重复创建消息。
- 没有浏览器通知权限时，应用内消息仍然可用。
- 用户应能关闭主动联系或通知。

部分	选择

- 用户直接修改优先。
- 模块边界支持更换模型和部署方式。
不要在没有发现明确问题时重新推翻整套技术栈。需要调整时，说明原方案存在的具体问题、替代收益和迁移成本。
