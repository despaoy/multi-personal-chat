# DeepSeek 后端链路阶段 55：保留完整的可用用户历史用于记忆检索

日期：2026-10-02。父提交：c008ab84d1923f5d434985bb78ee4e96bdbaf0c7。持续目标仍在进行。

## 根因与修复

已有完整用户历史中的话题位于长消息开头。动态上下文准备却只拼接最近六条消息中的用户消息，每条保留末尾 600 字符，并再保留合并结果的末尾 1200 字符；记忆服务又截取末尾 1200 字符。话题在候选检索前丢失，后续语义选择即使拥有更大预算也无法选择从未进入候选的原始约束。

服务器先修改两个业务文件：character_context 汇集当前已加载、授权的所有用户文本消息，排除助手和系统猜测以及非文本值；memory_service 将完整参考上下文加入检索查询。没有追加数据库读取或模型调用。最终选择与生成的预算、历史读取权限、来源收据、当前状态和删除授权规则继续生效。这里的“完整”指当前历史加载器已提供的用户消息，并非无限历史或无限模型上下文。

## 完整合成输入与证据

全部素材为虚构测试数据。旧的榆桐项目原始记录明确给出 RTX 3060、12GB、整周离线、禁止从零训练、已缓存且可启动的 0.6B 模型、完整权重/分词器/依赖、2400 条四类标注数据及 1920/480 的训练/验证划分，并禁止用验证集调参。另有同一用户、角色、私有范围内 36 条较新的完整库存记录，均明确不改变项目要求。3549 字符用户历史在开头明确讨论榆桐，之后是 45 条完整但无关的天气记录。当前请求是“按刚才那个继续，给我七天的执行安排。”来源身份、时间及历史均完整提供。

SQLite 和实际隔离 PostgreSQL 的零云调用比较保留同样的 37 条声明及 24 个候选预算：旧截断查询丢失旧项目，完整查询将项目带入候选。SQLite 修复结果 7/7；声明及原始记录不被改写。5 个新针对性单元测试首次执行全部通过，覆盖长消息头尾、超过六条消息的早期话题、角色过滤、非文本值和记忆服务实际收到完整查询。没有重跑这些已通过测试或全套回归。

真实 API 初次合成夹具只传入浏览器 history，未保存服务器历史。该接口按既定权限设计从数据库读取历史，所以这次输入缺失不能归为后端错误。保留原始结果和 5 次真实调用；随后只修正这一个新集成场景，将完整历史通过实际来源与消息接口保存，再执行一次。

修正后的隔离服务器请求使用当前 DeepSeek v4 pro，实际上下文窗口 65536。语义选择收到完整话题历史，旧约束来源被选中，其完整原始正文及话题进入实际生成请求。七天计划保留 RTX 3060/12GB、离线、已缓存小模型及禁止训练/验证集调参的要求。5 次真实调用全部 HTTP 200 且正常结束，后台数据库工作完成。两个尝试合计 10 次真实调用、2 个回答，均计入累计记录。

保存输出中的“不引入训练”最初被过窄的断言漏判；随后只修正断言并从保存的实际响应审核，未再调用模型。原始结果保持不变，另存审核结果 25/25。22 个保存结果反例均被拒绝，覆盖丢失话题、预算漂移、候选/来源缺失、证据截断、非当前状态、服务器历史缺失、模型/窗口错误、请求失败、错误硬件/联网/训练回答、记录改写、待处理写入及实际请求正文遗漏。该审核是明确合成夹具的条件检查，不能替代通用语义推理。

## 部署与同步

服务器先修复并验证，再仅重启后端，确认 ready 为 200 且实际进程继续使用原来的 DeepSeek 配置。其他服务、生产配置和数据库结构不变；没有生产业务生成重放。静态检查新增诊断为零，新文件格式及换行转换保留可执行 AST。验证后的八个文件按内容哈希同步本地及 GitHub main，并用同一提交更新服务器 Git 记录，不重置运行中的源码。

## 尚未验证的边界

更多历史会增加检索计算量，尚未进行吞吐量基准。加载器和最终模型预算依然有界。原始来源单独召回目前仍以当前请求检索，含省略指代的请求及长来源预算尚未普遍解决；本阶段成功的依据是实际选中的完整、当前且授权的项目记忆来源。并发删除/更新与跨批次快照，以及所有表达形式的语义正确性均未因此获得全面保证。测试中的硬件、模型资源与数据为合成条件，并未实际运行本地模型或硬件评测。
