# r113：完整字段查询复用读取契约，减少无效写入归纳

## 机制

此前每条准入用户消息都进入语义记忆归纳，包括刚执行过的纯字段查询。现在 scheduler 复用 `memory_query.lookup_fields` 的完整消息契约：仅在原分类与最终调度均为 idle、没有规则事实候选、且整条消息是已支持的字段读取时，沿用来源捕获路径后结束。不读取旧事实作为写入候选，不调用语义 writer。

没有增加问题分类模型、问号过滤器、关键词例外或提示词。原话仍保留，不改变回答阶段、查询执行器、读取范围和删除水位；也不假设所有问句都不含新信息。带陈述的混合消息、纠错、显式记忆/遗忘、未知任务、强制 immediate 调用保持原语义路径。

这是纯读取冗余的一部分修复，不是所有疑问句的通用语义识别。对开放计划查询、存储状态查询及省略指代的语义写入成本尚未解决；原话中的问题参与召回排序也仍需单独评估。

## 实际链路

fixture：`backend/evaluation/fixtures/read_admission_20260927.json`。5 个独立用户场景，共 6 条来源输入与 6 条问题；问题阶段清空近期历史，以实际长期读取回答。包含完整字段查询、复合查询、搬家陈述与提问混合、明确记忆指令、未识别开放问题。

使用实际 ASGI HTTP → prepare → 服务中的 Qwen3-8B-Instruct-AWQ → guard → 保存 → complete → scheduler。无 LoRA、RAG 关闭、可选复核关闭、隔离 SQLite；不是登录、浏览器、生产 PG 或全部模块联合验收。远端仅 `/home/boot/lhm/multipersonal-runtime/evaluations/`，未发布生产。

两组各 12 个 HTTP 请求全部 200。基线 12 次 writer，修改组 7 次：5 条完整字段查询均为 `source_only`、`source_capture=recorded`，0 writer；6 条来源输入及 1 条未识别开放问题仍各调用一次。明确记忆指令保持 hot，混合更新保持语义处理。基线 12 次 generation，修改组 11 次；后者包括 1 次确定性旧住址回答，不能把更少生成调用当质量提升。

两组是各自新鲜模型写入和回答，不是冻结写入输出的单因素质量消融。姓名、明确专业和社区安排问题可答；住址组回答存在波动，不能归功于准入修改。两组的复合专业/年级读取失败，混合搬家后都回复旧住址。

逐链路核对修改组发现：

1. 模型读懂了“我搬到赣州了，你还记得我叫什么吗？”，提出正确指向旧住址 ID 的 SUPERSEDE，但把整条含问题的消息作为 evidence。解析器 `memory_evidence_allowed` 因问句标记拒绝整个候选，accepted=0；不是 scheduler 跳过，也不是模型没读懂。
2. 完整新原话确实已保存，但“我现在住哪里”没有召回该搬家原话；旧住址 claim 对应的原话又因与事实相同而去重。最后没有来源上下文，确定性 `memory_lookup` 直接回答九江，未调用回答模型。
3. 复合专业/年级自述的专业候选使用 `kind=user_major` 而非协议 `major`，解析器拒绝；大三 claim 已保存且专业/大三整条原话也进入最终模型请求，但模型仍答无法确认。不能将这个阅读失败归因于上下文没有原文。schema 协议兼容、值呈现与模型阅读仍待分别处理。

上述解析拒绝已用真实记录重放定位具体 return 分支，0 新模型调用、0 数据库变更，脚本 `.tmp/mechanism-r113-parser-trace.py`。证据 `.tmp/mechanism-r113-{baseline,admission}-{traces.jsonl,manifest.json}`。
