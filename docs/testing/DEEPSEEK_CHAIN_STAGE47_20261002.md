## 根因与有效修复

`_mark_rebuild_dirty` 依赖进程内锁，分别读取修订号、写入加一、写 dirty。它不能协调其他进程；晚结束的旧读取可覆盖较新的修订号。读进程的已验证修订号恰好与回退后的旧值相等，便错误地走快捷路径。

原有重建完成的“读修订号再写 complete”也使用进程内锁，跨进程写入可能发生在两次数据库操作之间，旧重建任务因此可能覆盖新 dirty 信号。

新增两种数据库事务操作，SQLite 使用 `BEGIN IMMEDIATE`，PostgreSQL 锁定共享 config 修订号行：

- 递增实际修订号与写 dirty 在同一事务提交，失败一起回滚。
- 比较实际修订号与写 complete 在同一事务执行；旧或未来修订号不能授权完成，拒绝时不覆盖当前失效状态。

同步 PostgreSQL 适配器直接传递事务结果。API 的失效操作使用数据库事务，空库、实际重建和合法索引复用三个就绪分支都检查事务完成结果，失败不设置本地就绪或修订号。修订号格式校验在两种后端共用，不把错误状态重置为 0。没有新增表或迁移。

额外真实 PostgreSQL 检查尝试以旧修订号 7 完成当前修订号 8 的索引，实际返回 False，前后修订号及状态相同，不调用模型。
