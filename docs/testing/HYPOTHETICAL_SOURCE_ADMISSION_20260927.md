# r112：条件原话准入与真实 HTTP 冷读

## 结论

修复了真实完成入口把条件表达整体当作虚构、因而丢掉原话的问题。条件表达只保存为用户说过的话，不提升为确定事实，不调用语义写入模型。真实回答有改善，但检索覆盖和条件理解仍未合格；本轮不是整体人物模拟验收通过。

## 机制与边界

- 复用现有虚构检测，分离句首“如果／要是／假如／假设”的条件表达；后续仍有小说、引语、扮演等标记时不进入此路径。
- `complete_turn` 仅在没有规则事实候选时将此类输入标记为 `source_only`。关系备忘录命令、拒绝保存、敏感信息仍遵循原准入规则。
- scheduler 先执行既有来源捕获、范围和删除水位检查，再结束任务；不读取事实候选、不计算写入检索 embedding、不调用语义写入模型。
- `source_only` 表示没有事实归纳，不保证来源已保存；必须结合 `source_capture=recorded` 判断。缺少来源身份或不支持范围仍有独立诊断。
- 未改人物提示词、事实抽取语法或生产设置。原话召回仍默认关闭，测试显式启用。

## 验证方法

`web_memory_live_replay` 增加冷读问题阶段和案例选择，仍使用真实 ASGI HTTP → ChatGenerationService → prepare → vLLM 生成及 guard → 消息保存 → complete → scheduler。来源阶段使用实际数据库历史，问题阶段验证近期历史为空，只通过长期来源读取。

模型为服务器 Qwen3-8B-Instruct-AWQ，无 LoRA；隔离 SQLite，RAG 关闭，可选模型复核关闭，邻近来源半径 0。鉴权和排队使用测试适配，不覆盖真实登录、浏览器、限流、生产 PostgreSQL 或全部模块联合运行。

基线与修改组各 5 个来源输入、5 个问题，各 10 次新生成和 5 次写入模型调用。写入调用均来自问题阶段；条件来源保留本身没有新增语义模型调用。fixture 为 `backend/evaluation/fixtures/hypothetical_sources_20260927.json`。

| 场景 | 基线 | 修改后 | 判断 |
| --- | --- | --- | --- |
| 等录取通知后才报到 | 条件原话丢失，回答不知情 | 原话召回，回答尚未拿到通知、尚未报到 | 恢复条件依据，但对“是否决定”不够直接 |
| 等调岗批准再去工作 | 条件原话丢失 | 回答仍在等单位答复 | 有改善 |
| 假如首富就买岛 | 原话丢失 | 原话保留，但“我已经有自己的岛了吗”未召回 | 检索失败，不能算理解通过 |
| 明确小说情节 | 不保存 | 仍不保存；回答先说“没有”再说不知道 | 边界保留，答案仍过度确定 |
| 明确不要记住 | 不保存 | 不保存、不召回 | 拒绝保存边界保留 |

中文索引使用双字词元，“岛”单字没有形成重合。为区分检索与理解，另加“我说买一座岛，是已经买到了吗？”作为补充问题，保留原失败问题，不替换它。补充组 3 次新生成、2 次写入模型调用：

1. 原问题仍未命中，回答“你指的是什么岛？”。
2. 补充问题实际模型请求包含完整的“假如我是世界首富，我就买一座岛。”，同时包含上一条问题原话。
3. 模型回答“买一座岛，是已经买到了吗？……你是在问自己？”，guard 未拦截。

因此至少存在独立的检索覆盖缺口和有依据时未作答问题。补充组没有变成事实的 claim，但零错误事实不能替代回答质量验收。第二问不是单来源阅读隔离实验，因为上一条问题也已进入来源；后续需单独测量疑问句来源对排名和阅读的干扰。
