# 300条多轮对话测试设计 v1

这是为当前仓库逐项编写的**300个独立对话场景**，编号 D001—D300，分为20批，每批15个，每个场景3个检查步骤。多数步骤发送用户消息；部分步骤需要切换账号、检查数据库、重放请求或注入故障。共900个检查步骤，不把界面核对或回执重放虚报为900条新的用户消息。

**当前只完成设计与文件完整性核对，300例均未执行。没有软件通过率，也没有已确认的运行故障结论。**

从 [总索引](INDEX.md) 开始逐条阅读，或直接打开 [第1批 D001—D015](batches/01_D001_D015.md)。完整机器可读设计见 [cases.jsonl](cases.jsonl)。

## 每条用例包含什么

- 前置身份、入口、配置与必要测试夹具。
- 连续的用户输入、发送前操作和逐步预期检查。
- 应采集的链路证据和已经核对存在的源码排查入口。
- 独立编号、优先级、评估轨道与未执行状态。

没有预先生成“助手实际回复”。自然语言可以有多种正确表达，检查事实、约束、行为与证据，不要求模型逐字匹配某个漂亮答案。每步拿到真实输出并完成该步检查，再继续下一步；除专门的并发用例外，不并行发送同一场景的输入。

## 执行约定

1. **隔离环境**：使用可重置的测试数据库、索引与账号。每例从自己的前置条件开始；不同编号不继承记忆、缓存、历史或短期状态。本轮文档生成没有改动运行服务或真实数据。
2. **角色与身份**：A默认绑定实际注册的月社妃ID `tsukiyashiro_kisaki`；B绑定隔离测试角色，人物说明见 [夹具](fixtures.md)。U1/U2必须是不同可信登录身份；QQ/Telegram/群聊由事件提供真实不同作用域。不要仅修改请求 `senderId` 或 `sessionId` 冒充成功切换身份。
3. **入口明确**：普通文本质量用实际支持角色的生成入口。依赖持久历史、记忆的场景选择已确认会调用人物准备/完成流程的入口。Web正史、通用测试框、平台集成、假想分支分别记录，不能默认行为一致。测试框若只回传现场history，要记录这一事实。
4. **默认配置**：未另写时采用当前部署的默认规则记忆、`reply_guard_mode=lightweight`，实验性语义复核/记忆选择/策略选择关闭，假想分支关闭。运行前导出实际非敏感开关值核对；不是凭本文件替服务设置开关。涉及后台LLM记忆、strict、分支、实验选证、自动LoRA路由的用例单独运行。
5. **时间**：T0固定为2026-09-23 10:00:00+08:00；明确写了其他时间的用例覆盖T0。通过测试时钟或受控夹具推进，不修改操作系统时钟，不真等12小时。记录UTC时间与+08日期。
6. **状态可见性**：默认完成本轮回复及对应入口的提交后再发下一轮。后台写入等待可观测任务完成，不靠猜一个固定睡眠时长。平台须等发送成功确认；“发送调用成功”不等于用户已读。
7. **区分短期历史与长期记忆**：回答了前两轮事实只证明当前可用上下文足够。需要验证长期记忆时，额外捕获记忆库、召回与最终注入；标注“排除现场历史”的步骤必须真正去掉请求和服务端可见历史，保留所测记忆。不能仅关闭浏览器来假定已去历史。
8. **操作标记**：表格的“发送前操作”是测试人员/执行器动作，不是发给模型的句子。`operator_assisted`不是全自动脚本：先判断该步是发送、重放原事件、只读核对还是状态操作，按说明执行。回执重放或数据库核对的文本列只是核对提示，不应再生成一条聊天消息。条件不齐标 `blocked_fixture`，不猜测执行。
9. **模式与输出分开**：缺fixture、依赖不可用、预算校验、模型超时、机制失败、语义错误、体验不佳分别统计。失败请求也保留，不仅保存漂亮回复。
10. **数据用途**：这套是开发诊断集。用它修复后可以复测，但不能再当未见过的独立最终盲测集。没有自动加入冻结训练数据，也没有授权修改原作索引。

## 覆盖和边界

| 编号 | 主要覆盖 |
| --- | --- |
| D001—D060 | 人物身份、日常自然度、历史承接、任务意图、边界和收尾 |
| D061—D120 | 记忆提取、条件否定、版本删除、后台竞争、身份与作用域 |
| D121—D180 | 事项生命周期、时间歧义、关系备忘录、节奏和提示预算 |
| D181—D240 | 角色RAG、通用知识库、引用、输入安全、反事实分支 |
| D241—D300 | 网关送达、幂等、并发故障、Web历史、模型与实验配置、评测留证 |

对话能观察的功能是本套重点。文档上传、索引替换、界面删除、鉴权、故障注入、适配器选择和样本导出，需要操作步骤配合，不能仅对模型说“删除了”就算执行。模型训练数值正确性、量化效果、硬件吞吐、备份恢复、数据库迁移、所有浏览器兼容性不可能由这300条对话完整验收，仍属于独立工程检查。

用例中的“拒绝/说明未知/错误”不要求统一文案。仅在文档和现有源码有明确契约时检查特定状态码，如分支修订冲突409、角色与LoRA冲突422。其他场景先记录真实路由和错误契约，再判断。

## 预期属于哪一种

`assessment_track`是批次级初始标签；实际裁定应细化到步骤：

- `contract`：身份隔离、事务、边界或明确接口行为。优先用请求、存储、日志核查，不让模型自己宣布测试通过。
- `quality`：自然度、情绪理解、任务表达等用户体验目标。固定输入与配置，可重复采样并人工裁定；不将一次措辞差异叫作程序缺陷。
- `boundary_probe`：已知规则能力边界及邻近表达。安全保守地未识别可以标 `known_limit`；错误写入、串主体、旧状态复活等仍是需要定位的问题。
- `mixed`：同一例既核查机制也评价回复，需要分别给结论。

诸如跨句条件合并、复杂否定、下周三、小时级事项、同义事项归并，不预设已经实现。作用域晋升用例需要实际支持且已启用的写入路径。没有该路径时标未适用或能力缺口，不能据此编造软件已经支持。

P0表示优先检查数据隔离、破坏性状态错误、真实安全或核心交付；P1表示主要功能和质量回归。当前优先级按批次给出，执行中可以对具体失败重新评定严重性，不能把整批所有措辞问题定为P0漏洞。

## 如何用对话定位链路

| 层级 | 必看证据 | 最早偏离的典型表现 | 下一步 |
| --- | --- | --- | --- |
| L0 界面/平台输入 | 输入原文、选中角色、请求payload、事件身份 | 字被吞、角色没传、旧history串到新会话 | 检查输入事件、状态清理、网关规范化 |
| L1 鉴权与范围 | 登录主体、平台/适配器/群/发送者、归属校验 | 查询条件已指向别的用户或会话 | 检查API身份绑定与scope构造 |
| L2 队列与幂等 | trace、队列时间、锁键、回执状态、调用次数 | 同一事件生成两次、同会话乱序、锁未释放 | 检查入队、复合键、失败恢复 |
| L3 状态读取 | 原始历史、记忆版本、事件、备忘录、有效期 | 正确数据未读取，旧版本或过期状态出现 | 检查持久化及生命周期过滤 |
| L4 理解与检索 | 规则提取、极性、候选、query_analysis、原始证据 | 提取反义、检索错主体、把主人公当主仆 | 检查抽取、域门控、召回与排序 |
| L5 提示组装 | 最终实际消息数组、被舍弃ID、完整条件、预算 | 候选正确但没注入、尾部否定被截、参考进system | 检查编译、转义、预算与证据包完整性 |
| L6 模型与守卫 | provider/model/LoRA、原始生成、守卫前后、调用数 | 提示完整但答错；守卫将正确回复替换为不合适兜底 | 分开复测原始生成与守卫规则 |
| L7 写入与送达 | 事务、版本、平台send、delivery、计数 | 回复对但没落库；未送达却写记忆；重试重复写 | 检查complete_turn、事务与回执边界 |
| L8 展示与评测 | 返回JSON、最终气泡、引用卡片、评分原始记录 | 后端正确但UI残留旧引用；失败被剔出分母 | 检查响应消费、展示及指标计算 |

先找**最早出现偏差的一层**。例如“回复仍说喜欢咖啡”至少有四种不同原因：没写入否定、检索到旧版本、注入丢掉否定、模型无视正确证据。仅凭最终回复不能确认根因。用例里的源码链接只是候选入口，并非判定这些文件有bug。

一个缺陷记录至少包含：case/step、预期与实际、最小复现输入、运行清单、原始证据路径、最早偏离层、待验证假设、能区分假设的复测、修复后同例结果。未获得中间证据时写“原因未确定”。

## 结果记录与判分

复制 [results.template.jsonl](results.template.jsonl) 到独立运行目录，**不要直接填这个模板**。模板包含300条 `not_run` 记录。每次运行新增文件，禁止覆盖旧证据。`build_suite.py`会重建模板，实际结果必须放在其他目录。

建议逐步使用：`pass`、`fail`、`known_limit`、`unknown`、`blocked_fixture`、`not_applicable`、`not_run`。机制与语义分开记录。质量按0/1/2分评：0=违反关键意图或明显错位；1=完成意图但表达机械或部分遗漏；2=自然完整且有依据。质量分不替代隔离与安全判定。

例级通过要求所有适用关键检查通过；任何关键失败则失败；尚有未知或夹具阻塞则不可宣称通过。报告必须同时列300例中已执行、未执行、阻塞、未适用、已裁定、未知数量。通过率仅对已裁定适用样本给出，并注明分母；超时和服务失败不能从运行结果隐藏。文档校验通过率不是软件通过率。

每次运行清单记录：代码commit与dirty状态、补丁摘要哈希、用例哈希、测试数据/索引哈希、模型及权重/LoRA版本、画像版本、provider、采样参数和seed、最大上下文与输出预算、全部相关功能开关、数据库后端、测试身份映射、时区、硬件与服务版本。日志保存测试信息，认证令牌和真实凭据不进入清单。

真实模型质量用例建议先单次发现明显问题，再对不稳定样例固定设置做3个seed复测；不能挑最好的一次。模板与结构测试可用mock，但mock不能证明真实人物自然度、语义理解或真实服务延迟。

## 边界夹具的确定构造

- D026：在首轮后插入30个问答对。用户第i句=`这是背景闲聊第{i}轮，今天整理了一页纸。`，助手第i句=`收到第{i}轮分享。`，i=1..30。确保确实进入被测历史来源，并捕获最终请求确认首轮已不可见；只在客户端插入但入口不使用该history不算完成前置。
- D029/D115等跨conversation测试用真正不同的群/频道或仓储conversation夹具。私聊被规范化到用户身份时，相同用户换sessionId可能仍是同一范围，应作为正确规范化行为记录。
- D089长句：读取实际句长阈值N，以无句号片段`这是一段背景说明，`填到N+32字符，末尾追加`但结论是我不喜欢咖啡。`。只构造一长句；核查不应先截尾再保存错误极性。
- D175、D177等窗口与预算：正文、ID、顺序、长度存为该次运行夹具。填充语句采用上面的确定模板。每个边界跑N−1/N/N+1三个子变体，编号保留主case并加后缀；不计为额外独立对话凑数。
- D218空白：发送真实的3个空格、真实换行加制表符；不要发送`<空白消息>`字面文本。D219依据实际schema的字符/字节计量构造上限±1；D270依据token估算预算另测，不混淆两种限制。
- D176超长备忘录：前缀`沟通设置：`，重复`保持自然。`使关键句`不要问我的收入。`从第301字符后开始；捕获实际截断。用例当前消息也给禁问边界，以区分短期遵守与持久注入缺陷。
- 并发、后台删除、生成后提交失败：使用受控屏障，保存挂起位置和放行顺序，不依赖不确定的网络速度。只在临时服务/数据库注入故障。

## 设计依据与生成

设计核对日期：2026-09-23。基于当前工作区及HEAD `57aede2b490887bd70225bd0c0af13317ca06f8b`；设计时工作区已有用户修改，因此此HEAD不单独代表全部当前行为。已阅读README、CURRENT_STATE、M1/M2、自然关系、对话节奏、角色检索、分支、平台回执文档，以及当前生成/上下文/事件实现和现有链路回归用例。

文档中较早的M1说明尚未有事件生命周期，而随后M2和当前源码已实现；本套以较新说明与源码为依据。例如事件进行中存储值为`ongoing`，不是将用户可见词直接当字段名。

人工逐条编写源文件为 [authoring.txt](authoring.txt)，构建器为 [build_suite.py](build_suite.py)。它仅转换文档、验证编号/字段/分组/源码路径和重复输入，不发送聊天，不执行模型，不做数据库操作。D179与D180故意保留相同输入，作为lightweight/strict模式对照。

从仓库根目录运行 `python docs/testing/dialogue_suite_v1/build_suite.py` 可重建20个批次、索引、JSONL与空结果模板。[validation.json](validation.json)给出本次离线完整性核对以及源文件哈希。
