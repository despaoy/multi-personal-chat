# 第108阶段：闭合原话读取不被目的说明和输出要求扩大

本阶段修复明确原话读取范围之后的解释误回退。读取动作、读取的目的与回复要求需要区分：`读取完整原话仅用于取得核对依据`、`已读取的原话作为核对依据`及`同时保留第三方主体，并且核对这两份目录的原始字段`不会声明其他来源。真正新增、否定或未明确来源的读取继续保守处理。

## 因果证据与修改

第107阶段首次准备完整任务时已发现，说明文字里的读取动词或“同时”会令闭合字面范围变为未知，额外合并大范围历史，完整原话因预算被排除。本阶段没有再改写测试描述绕过问题：

- 三个新完整因果节点先失败，服务器修改后通过，分别覆盖名词性目的说明、并列输出条件、已知资料加预期未知部分。
- 新边界首次22通过、1失败，发现“这两份目录的原始字段”把“原始”误判为来源对象；保留失败并把来源对象与字段说明区分。
- 准备原生任务时，原样描述“完整读取的原话作为核对依据”再次触发范围检查。新增完整独立因果节点先失败，补充过去读取的名词性引用后通过；另外三个新边界证明这种表达不能豁免新增、其他或否定读取。
- 共30个新的受影响唯一节点已通过；相关文件静态检查无问题，未重跑项目全套或旧付费用例。

一处生产模块`memory_source_search.py`将闭合范围的尾部判定改为动作与引用的区别。名词性目的引用只允许裸原话对象或明确指向已声明证据的对象，配合限制性目的词；过去读取的引用要求作为核对等依据。新增、否定、其他或不同来源的前缀不能被这种解释豁免。连接词单独出现不再等同额外读取；同时检查新增动作及不明确来源对象。引用材料先被遮罩，不能取得命令权限。SQL绑定、同条AND与组间OR、权限、状态及删除围栏保持原样。

## 真实数据库与模型验证

隔离PostgreSQL只读对照核验原实现单独读取声明已经能识别同条AND及任一OR；仅添加目的和输出说明才令范围失效。真实原话、权限、近期历史及预期数据全部相同：旧路径两项都是查询62、历史62、并集62、`budget_omitted`；新路径分别完整读取1条/8082字符和2条/16017字符。两份40条数据的完整原文各6863字符，均在实际16条近期消息之外、无MemoryItem链接。

两项新的原生任务使用官方DeepSeek Flash，复用真实6条记忆、20轮历史的问答前快照并递归核验来源。任务核对新条目031或032的全部字段、完整前提及例外，逐项判断明确路线、容量与已核验条件；两份目录比较费用及时限，实际办理未知。完整语料提供全部必要信息，当前问题没有再次提供费用、时限、容量、核验值、前提或例外。问题中的原始目的说明及输出描述进入真实主模型输入，没有测试后改写、预填答案或裁剪原文。40/80条原数据完整在实际主模型输入中，16条历史、65536窗口及2048输出限制保持原样。

初次自动回答检查为17/18，原因是检查器只认中文条件名，而保存回复对两条目标均明确列出中英字段、正确路线、容量阈值、核验值及满足判断。原回复与当前问题不改写，按每个目标条目及中英字段别名核验，同时用六个独立正负测量例拒绝错误阈值、其他编号、负判断及仅字段无判断；保存初次结果及回复哈希。这是测量修正，没有重新调用模型。原生链路及快照检查50/50，修正测量后的自动回答检查18/18。两项原生HTTP200都实际调用主模型一次，共7次官方云请求，包含全部辅助调用，全部HTTP200及正常stop。费用按真实usage及缓存统计，沿用项目已核对的人民币非高峰系数（每百万缓存输入0.02、未缓存输入1、输出4），估算0.21220732元，属于用量估算而非账单。全量调用统一计入，未设置最低消费或重放历史/成功付费用例。
