# DeepSeek backend chain Stage36 — truthful deferred memory deletion

Date: 2026-10-02. Previous synchronized commit: 6d35f71126380c481c69642cdcfccd207052118d.

Stage35 saved actual signed integration replies denied the available personal-memory deletion capability, although the exact subsequent delivery worker receipt reported erased with persisted=2. That evidence was reused without replaying either previous answer or source writes. The generation path deliberately defers deletion until successful physical delivery; its context contained the general prohibition on claiming an operation without an execution receipt, but omitted the actual backend delivery plan. The model consequently treated missing execution evidence as missing capability.

The fix adds a distinct, server-owned generation-only memory_operation_deferred flag. The API sets it only when delivery completion is configured, persistence is enabled, the request is outside a branch, normal character preparation succeeds, and both the existing source safety gate and explicit erasure intent gate accept the current message. A fixed system policy describes scoped authenticated personal-memory handling separately from administrator commands: after this reply's delivery confirmation the backend will resolve authorization and targets and attempt deletion. It requires a truthful acknowledgement without claiming completion or guaranteed success, and preserves questions unrelated to deletion. User text, nickname, history, and retrieved data cannot create this flag. Preview and immediate Web execution do not receive the deferred policy.

The flag is neither a compiled nor a prepared execution receipt and is absent from the frozen completion snapshot. Both actual receipt fields remain empty before delivery, ensuring that post-delivery completion still performs the real semantic operation. No deletion is executed during generation. Existing source clocks, owner scope, erasure whitelist, fences, sensitive-content gate, delivery worker and actual execution receipt remain authoritative. No schema or provider configuration changed.
