## 服务器修复与范围

仅修改 `character/memory_service.py`，新增时窗路由用的 `_historical_query_text`。按明确句子/分句边界识别完整第一人称出生日期陈述，包括“我出生于某年”“我在某年出生”“我是某年出生的”“我的出生年份/日期是或为某年/月/日”。这类日历日期绑定出生事实，在计算记忆时窗前移除该完整陈述的路由信号；真实原始 query 仍用于相关性、选择器、来源回查、事实提取与最终生成，不移除最终问题或替用户改写事实。

不把未知句式和出生疑问句当成已解析陈述。“我出生于1998年时住在哪里？”仍按 1998 年历史范围；“我出生于1998年。2015年我当时的住址是什么？”按 2015 年；具体 2026年9月 与“去年”提问仍保留各自窗口。不会因为出现“现在”就一概取消历史查询，不改 explicit include_historical 的控制接口。

复用既有 SQLite 原始库，不重写来源、不重新写记忆。完整出生陈述问题与当前控制问题现在返回相同的 active 淮安 ID 和来源，更正原文可回查，旧宁德不作为当前记忆进入选择。存储版本和全部表摘要均保持不变。

13 项新增测试通过：六种独立出生陈述/分隔/日期写法，五种真实历史时间与疑问句，未知或引用句式的保守处理，以及真实规则更正、来源关联、跨用户隔离和读取不改版本链。直接受影响的既有历史版本链用例 1/1 通过。只执行这 14 项，没有全套回归或已通过业务用例重播。

真实 PostgreSQL 库创建前核对实际 data_directory，从既有已审核的纯合成库克隆。新普通用户认证，私聊范围固定为用户 ID；真实 capture_source 与规则提取/写入建立完整两份来源和新旧住址，设置时间为服务器当前时钟前一天/前一小时，并在发问前独立只读核对持久化。该设置验证真实读取和选择链路，没有用模型预生成这两条种子，也未改生产或伪造已注入的记忆。SQLite 的固定可复现时钟与 native 的实际服务器相对时钟分别记录，没有混称字节相同。

最初测试采集器用 max_tokens=2048 判断主回答，但实际记忆选择器也使用 2048。选择器的 JSON 输入因此被错误要求含 character_memory 区，被采集器拦截并回退；后续主请求因缺少当前记忆又被完整输入检查拦截。初次未保存足够的准备信息，第二次仅观察这个失败用例，保存候选、上下文和实际请求后确定：召回确实 selected_count=1，但选择器 fallback，原因由采集器造成。此错误不作为后端缺陷。

修正采集器：2048 输出预算加规范 `<user_query>` 请求标记共同识别主回答，选择器 JSON 调用单独计数。只重试这个失败新用例，输入原文、预期、后端修复和模型不变。没有移除出生年份以获得更容易的通过，没有放宽主请求中的当前记忆要求。

最终 native 实际当前淮安 ID=41，旧宁德 ID=40；真实召回 1 个当前候选，选择器 selected，当前 ID 进入 character_memory，historic=false、active、SUPERSEDE 和准确 stage64-correction 来源保留。完整出生陈述和问题仍在规范最终用户请求中，来源/个人事实不进入系统指令，动态策略 applied、普通历史为空。DeepSeek 回答“你的现居地是淮安。”，指代正确，没有把出生年份变成住所时间或采用旧宁德。

成功实验 4 次真实 DeepSeek 请求与响应均 `deepseek-v4-pro`、HTTP200/stop，包含一个独立的 2048 选择器调用和 1 次完整主回答。加上前两次采集失败各 1 次策略辅助调用，阶段总计 6 次 HTTP200/stop、1 次实际主回答尝试/完整回答；两个失败没有实际发送主回答。没有遗漏失败计数或重播已通过模型用例。
