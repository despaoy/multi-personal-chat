# DeepSeek 后端链路第 13 阶段：完整原文与字段来源绑定

2026-10-01。基线提交 `37c472671abd82bb5592f98893f8701e10d472a0`。先在服务器修改、验证和部署，再将有效文件同步本地与 GitHub。遵循只测修改部分的要求，本阶段没有运行全套测试，没有重复已通过的模型用例。

## 问题与根因

已有合成账号的姓名、来源地、现居地、专业都有完整原始输入。DeepSeek 回答四项资料正确，但后端把来源地与专业标为尚未核实。共享原文为：

> 请跨会话记住，我叫岚舟，我的老家在宣城，目前住在丽水，大学专业是环境工程。这四项资料都是我本人的。

语义记忆分别保留了“我叫岚舟”“我的老家在宣城”“大学专业是环境工程”等片段。旧读取器缺少老家别名及完整原文的主体承接，只认独立的第一人称完整字段。模型提出的时间端点与置信度不能代替来源证明。

部署前对实际完整住址更新只读检查，发现第一版修复会把住址退回未核实，因此没有部署第一版：

> 请跨会话记住，我目前住在舟山，已经不住丽水了。老家仍是宣城，大学专业仍是环境工程。只更新目前居住地。

补齐承接和更新范围后，投影能够识别字段，但直接字段读取器仍使用旧解析器。另一个针对性反例发现，旧字段投影使用批次共享来源池时，一条仅有引用 ID、未实际关联来源的记录可以借用另一条记录的关联证明。

## 最终修改

- 完整原文读取器逐句理解，保留完整证据及原始字段片段；识别老家/故乡/家乡、大学专业、明确主体承接、仍保持的字段及已声明字段的更新范围。不受规则写入的四条上限影响。
- SQL 来源读取保留实际 `memory_id` 关联；语义和旧字段都按每条记忆自己的授权关联读取，不把模型引用 ID 当成授权。继续使用原有账号、角色、会话范围及撤销边界。
- 每个实际来源都须支持该字段的唯一值，原片段必须属于该来源；缺失来源、他人主体、假设、时间限定、尾部撤回、未知后缀、冲突和读取异常保留为未核实。完整未知原文仍可用于召回。
- 字段状态与直接字段回答使用同一完整来源语义。读取投影不重写数据库中的证据、原始键、时间端点、替代关系和 ID，不补造不存在的其他字段记录。
- 原生评测支持同一真实来源关联多个字段，以及按用例指定状态询问和预期字段；本阶段只选择两个新用例，既有用例不重复运行。
