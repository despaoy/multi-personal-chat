# DeepSeek 后端链路优化：第七阶段（2026-10-01）

本阶段在服务器先修复并验证知识问答、模型选择和生产启动检查，然后同步回本地及 GitHub。服务器运行中的后端现已选择 `openai_compat / deepseek-v4-pro`；长期记忆模型写入、动态上下文语义复核和上下文记忆选择已开启。没有进行模型训练。

## 根因与修复

1. `/api/ask` 优先按本地 vLLM 配置是否存在决定生成器，没有遵循模型管理器当前选择；云模型路径还会压平消息角色、遗漏采样参数。现在按当前 provider 选择生成器，DeepSeek 收到完整 system/user 消息及 temperature、top_p、输出预算，返回真实所选模型标识。保留本地模型原有延迟初始化。
2. 原生多粒度检索引用使用 `id`，证据包只接受 `source_id`，导致正确卡片已找到却全部被丢弃，模型调用数为零。现在兼容这两个输入字段；两个字段冲突或没有匹配卡片时仍拒绝绑定。来源标题、文件和行范围由实际匹配的检索卡片生成。
3. 生产启动检查无条件要求 vLLM 地址，拒绝完整的 DeepSeek 配置。现在选择 `openai_compat` 时检查它自己的地址、模型和凭据；选择默认或显式 vLLM 时仍要求本地服务地址。

两个完整问句：

- “请查月社妃的身份资料，说明她对应的魔法之书，并附上来源标记。”

原生测试还对第一个问句调用 `/api/ask/stream`。修复前两轮共 6 个问答请求没有调用 DeepSeek，因为证据包为空。修复后隔离 PostgreSQL 上的 2 次普通回答和 1 次流式回答，实际发出 3 次 DeepSeek 请求，全部 HTTP 200、模型 `deepseek-v4-pro`、结束原因 `stop`；13 项链路检查通过，包括消息角色、采样参数、正确书名、引用及未调用错误本地模型。

生产进程通过真实管理员登录后的认证直连接口，再次完成两个普通回答和一个流式回答。9 项独立检查通过：HTTP 状态、正确书名、`document_id`、源文件、行范围、当前模型及流结束。原始响应保持不变。最初检查器错误使用内部 `source_id` 验证公开引用，已按公开接口实际使用的 `document_id` 修正独立审计；没有更换问句或放宽来源要求。
