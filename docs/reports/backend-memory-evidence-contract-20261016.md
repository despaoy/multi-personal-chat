# 记忆证据与来源元素使用明确契约

本地基线：`aa43de3291c5c5ee847764a141fa316b8e3b8e4e`。继续遵守当前先本地修改、验证后按阶段同步 GitHub 的指示。

## 实际问题

仓储只检查证据和来源 ID 的外层数组。证据读取随后递归猜取 `text/content/quote/evidence/summary`，还会把数字、布尔值转换为原话；来源元素也会隐式转成字符串。隔离 SQLite 基线证实，含任意摘要对象的证据读取未报错。

调用与数据格式检查发现，`source_event/source_events/adjacent_event/adjacent_events` 四个自由字段没有项目内生产者和数据使用方。另有明确使用的结构化引文 `{message_id, quote}`，需要保留。

## 修改

- 仓储只接受非空文本来源 ID；证据元素接受非空文本或字段明确、文本完整的 `{message_id, quote}`。空列表和缺失的可选旧列保持合法。
- 同一检查用于读写。写入在数据库操作之前验证，避免先持久化损坏记录，再在读取返回值时失败。
- 读取层直接消费已经验证的文本或明确引文字段，删除递归猜测、摘要字段回退、数字文本化及无使用方的四个自由字段读取。
- 有来源 ID 的关联事件仍走已有授权记录及生命周期校验，不通过邻接字段猜测。原始 JSON 列保持原样，不自动修复或迁移历史数据。
- 类型声明对应实际支持的文本和结构化引文格式。原生数组读取的来源列表会复制后合并旧单来源，避免修改输入快照。

生产代码净减少 3 行，实际删除了 29 行宽泛证据解释逻辑，新增的检查集中在仓储边界。

## 定向验证

24 个不同用例分批通过，只运行新增、修改和必要关联检查：

- 10 项完整 SQLite 故障控制：证据及来源数组中的布尔、数字、摘要对象、嵌套数组、空白元素，在精确读取、作用域列表和实际召回入口均报出安全字段错误，原始记录不被自动改写。
- 2 项写入拒绝：坏证据与坏来源在持久化前失败，原数据库记录保持一致。
- 1 项正常结构化引文：真实来源捕获、带归属引文写入及读取、作用域召回均保留完整条件和例外。
- 2 项正常旧格式及召回：合法空列表、单来源、关系、置信度、有效期和解码证据保持语义。
- 5 项证据关联：JSON 外观原话原样往返、正式字段不混入旧原始列、完整关联事件及读取版本绑定。
- 4 项权限及生命周期边界：关联事件不能复活被删除、撤回或未确认记录。
