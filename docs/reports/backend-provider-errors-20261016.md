# 模型 HTTP 故障安全传递到业务入口

日期：2026-10-16。基线：`9f9caeb0201f7efcf50bacb6c35f5d27e8f1811f`。

## 实际问题

服务器隔离预检用真实 SQLite 配置、OpenAICompatProvider、问答服务及 ASGI 接口，外部 HTTP 由 MockTransport 控制为 401。普通问答返回通用 HTTP 500、“服务器内部错误”；SSE 返回 `meta → error/internal_error`。上游状态被压成普通 RuntimeError，调用方无法可靠区分认证、限流与其他故障。全局处理器还直接记录异常字符串，可能把非模型异常中的私有细节带入日志。

主聊天、角色准备和检索审核也各自包装错误。直接沿所有异常链寻找模型故障并覆盖外层错误，会丢失必需调用记录失败的状态，以及已经执行的记忆操作回执，因此没有采用这种全局替换。

## 修改

- OpenAI 兼容 provider 对非 200 响应抛 `ProviderResponseError`，只保存数值状态和安全字符串，不保存响应正文、完整 URL、请求头或密钥；成功路径不变，没有重试或切换模型。
- 普通问答和 SSE 共享该异常的安全描述。401/403 显示认证失败；402 显示余额问题；429 显示限流；其他拒绝保留 HTTP 数字并提示检查服务。上游认证失败对本站返回 502，避免触发用户登录用的 401 注销；402/429 返回 503。已经开始的 SSE 保持 HTTP 200，以明确 error 事件终止，不产生正文或 done 成功事件。
- 主聊天直接模型拒绝同样显示安全原因。记账失败、执行记忆操作后的上下文失败及检索审核失败，仅在原有详情上附加 `providerError`。原 HTTP 状态、阶段、消息、保存状态和执行回执均保留；未匹配到该异常时维持原行为。
- 因果追踪只用于这些已确认的业务边界，并且只识别明确异常类型，不解析异常文案，不把一般 PermissionError/RuntimeError 当成模型认证问题。全局未知错误日志改为记录异常类型；模型错误日志记录安全类型及 HTTP 数字。
- 现有云端链路测试只更新本次有意改变的 HTTP 拒绝状态为 502，并增加 kind/上游状态断言；截断、传输故障的既有失败预期保留，没有放宽断言。

## 验证

服务器 32 项直接相关测试通过（5.23 秒），随后仅新增余额分支普通/SSE 2 项通过（2.73 秒，其他 15 项未选中），合计 34 项。没有重跑此前证据投影和熔断精简的已通过测试组。

覆盖真实应用工厂、路由、provider HTTP 边界、请求上下文、缓存、真实 SQLite 调用记录/归档、实际删除后的回执，以及默认检索规划器→审核适配器→模型拒绝→业务包装的原因链。成功响应保持正常；失败没有缓存、没有替代模型、只发起一次测试 HTTP 请求；客户端和上下文均清理。私有正文、密钥与 URL 的合成哨兵不进入响应或日志。

HTTP 响应和操作解释是明确的测试控制，不是实际 DeepSeek 模型验证。涉及的事实输入完整，实际删除只作用于临时测试数据库。语法、补丁空白和增量静态检查无新增问题。未运行全量回归，未发起付费模型请求。

## 交付与限制

沿用服务器修改和定向测试后同步本地、阶段提交 GitHub 的流程。部署仅重启后端，要求 `/ready` 为 200、配置文件哈希及其他服务进程不变，文件逐一核对 SHA-256。

本阶段处理 OpenAI 兼容模型 HTTP 拒绝的安全展示，未将网络故障、超时、无效模型输出或独立记忆写入客户端强行归入同一类型；这些情况仍报错，后续继续分别审查。外部聊天平台对错误的二次包装也尚未全部统一。上一阶段真实 DeepSeek 正常配置的认证失败仍待用户更新凭据，本阶段没有再次请求它，健康检查不代表认证恢复。
