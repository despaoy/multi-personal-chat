# 模型配置接口的安全错误与部分完成状态

基线：`71a364995fd75368ff822e32d31180ccb1002495`。

## 问题与修改

`backend/api/config.py` 的模型状态接口原先记录原始异常及堆栈，提供商切换接口直接把 `str(exception)` 返回给调用方。隔离复现还确认：运行时提供商已经切换、配置保存失败时，没有说明已经完成的操作。原有 `if success/else` 分支也没有有效失败来源：实际 `ModelManager.set_provider` 只会成功返回 `True` 或抛出异常。

模型状态读取改用现有有界执行器，失败返回安全的 503，并保留原异常原因。提供商切换按原有顺序执行选择、持久化、缓存失效、必要的运行时刷新和状态读取；删除不可达失败分支及原始异常日志/响应。成功响应格式保持一致，业务源码增加 39 行、删除 44 行，净减少 5 行，无新依赖。

系统错误返回 503，包含当前 `stage`、`providerSwitched` 和 `configPersisted`。两个操作状态的 `false` 表示尚未执行，`true` 表示已经确认完成，`null` 表示开始操作但未能确认结果。例如，数据库可能已经写入但提交确认失败时，不能声称“未保存”，也不能声称“已保存”。异常原因继续保留；不会为错误响应自动切回其他提供商或伪装成功。

非法 JSON、非对象请求、未知或环境禁止的提供商仍属于明确的 400 请求错误。配置更新、敏感值遮罩、服务端配置保护及管理员鉴权未改动。

## 验证与限制

22 项定向检查首轮通过：19 项新增检查覆盖安全状态错误、执行器、无效请求、各操作阶段失败、持久化确认丢失、两个合法提供商的成功路径和实际 HTTP 部分完成响应；3 项现有检查覆盖配置解析来源一致和运行时刷新失败的持久化状态。原有测试与断言没有修改，没有重复全量回归。

通过 Python 3.10 语法解析、差异空白和 Ruff E9/F 增量检查。AST 对比确认修改限于两个模型接口及日志导入，实际模型管理器源码未变；原始 `set_provider` 的只成功返回契约另行核对。测试使用完整隔离对象及临时数据库，真实模型调用为 0，没有切换生产提供商或修改生产模型配置。

服务器更新后，就绪与前端登录页面返回 200；匿名受保护接口返回 401，安全响应头正常；运行配置和其他服务进程不变。本阶段没有执行实际生产提供商切换，不作为并发管理操作原子性或真实模型能力验证。整体优化目标继续进行。
