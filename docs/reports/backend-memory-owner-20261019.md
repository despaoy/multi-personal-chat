# 后台记忆缓冲的存储归属修正

基线：2ab914af629d59638a4f3537c538fc45eb6415bc。

## 实际问题

沿请求上下文构建、仓储、后台缓冲、即时操作、模型处理、写入回执和停机流程审查后，确认缓冲键使用仓储包装对象的身份。应用自有数据库的请求或上下文预算重建可以产生多个仓储包装，即使它们引用同一个数据库依赖。

即时操作只会先提交同一缓冲键的旧消息。因此，同库、同角色、同用户的两个包装可能让新更正先进入队列，旧消息仍留在另一个空闲缓冲中，稍后才进入模型和持久化流程。

服务器使用真实 SQLite、正式仓储和完整后台调度器复现：旧饮品偏好先提交为空闲任务，新更正后提交为即时任务，实际顺序却是 newer、older。

## 修改

仓储契约明确提供 storage_owner，只读返回已有的持久化依赖对象。调度器按该对象的身份、角色和既有用户范围组织缓冲，仓储包装的生命周期不再改变同一存储中的消息顺序。

即时任务复用原来的同范围预提交机制，先提交旧缓冲，再提交当前任务。不同数据库依赖或用户继续独立缓冲。现有平台、适配器、角色及会话范围字段保持原有定义。

生产代码新增八行，用于明确存储归属；没有新增分支检查、重试、排序补丁、语义规则、配置或缓存。记忆解释、写入事务、来源校验、撤回与回执处理均未修改。

## 验证

- 三组真实数据库前后对照：同库同用户、不同数据库、同库不同用户。正式工作器执行来源捕获、旧记忆读取、提示词构建、结果解析和回执完成。
- 同库同用户从 newer、older 修正为 older、newer；即时入队后旧缓冲已清空，队列包含两项任务。不同数据库或用户仍保留一项独立缓冲和一项即时任务，处理与隔离行为前后一致。
- 两条完整消息分别包含原偏好、明确更正、否定和适用范围，来源原文与回执均完整保留。模型边界为明确的空候选测试控制；每组两次受控调用，结构化写入数为零，没有将该结果解释为真实模型理解质量验证。
- 定向测试共 862 项，最终全部通过。初次为 823 项通过、39 项失败；五处内存测试仓储缺少新归属契约，补齐后仅复测这 39 项，全部通过。已有隔离 PostgreSQL 配置在首次运行即完整启用。
- 原容量与顺序测试增加“同一存储的不同仓储包装”参数，新增一个直接回归案例；原容量、顺序、取消、错误及持久化业务断言保持原样。其他测试替身只补齐显式存储归属。
