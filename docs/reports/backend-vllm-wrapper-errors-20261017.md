# vLLM 客户端故障明确传递，删除重复状态

基线：`7f6cb5269071b8d7aed2382c9851935851962bad`。

## 问题与修改

`backend/api/generate.py` 的共享客户端包装原先捕获初始化故障后返回 `False`，状态接口因而返回成功的 `enabled=false`；关闭失败也只记录警告并正常返回。隔离复现确认两种故障均被隐藏。包装还维护没有运行时读者的 `_vllm_initialized`，与客户端是否存在重复。

现在，明确关闭 vLLM 功能仍可正常返回未启用；已启用时初始化失败返回安全的 503，保留原异常原因，不记录可能含私有连接信息的原始异常文本。仅在成功取得非空共享实例后保存引用，后续独立请求仍可重新尝试初始化，不在当前失败请求内隐式重试。状态查询异常同样明确返回 503。

关闭过程删除吞错分支，原始失败交给现有生命周期清理器，供其继续关闭其他资源并保留异常链。取消继续传播。删除全部重复初始化标志；客户端引用、现有循环所属锁及共享所有者维持原来的职责。业务源码增加 16 行、删除 28 行，净减少 12 行，无新依赖。

## 验证与范围

18 项定向检查首轮全部通过：12 项新增检查覆盖明确停用、并发复用、三个入口的初始化失败及后续请求重试、空实例、初始化取消、状态探测故障、关闭故障与取消、正常关闭后重新初始化及实际状态 HTTP 503 边界；6 项现有检查覆盖循环重建、共享客户端重建、启动和关闭多故障的异常链及正常资源清理顺序。

原有“临时初始化失败后恢复”测试原先要求失败变成 `False`。按照本次明确失败的业务契约，将该断言加强为 503、原异常原因和空客户端状态；后续成功及尝试次数断言原样保留。其余测试未修改。没有放宽有效检查来接受失败，没有真实模型或外部服务请求，也没有重复全量测试。

修改通过 Python 3.10 语法解析、差异空白检查和 Ruff E9/F 增量检查。AST 核对确认除了三个客户端生命周期/状态函数及重复标志之外，生成 API 实现一致；共享客户端所有者和应用资源清理器源码未改动。服务器更新后就绪及前端登录页面返回 200；匿名受保护接口返回 401，安全响应头正常；配置和其他服务进程不变。

本阶段使用隔离客户端及完整故障注入，未向生产 vLLM 发起推理或状态请求，不作为真实本地模型能力验证。现有多实例逐项健康结果保持原样，没有把明确的不健康实例当作异常格式处理。当前配置的 DeepSeek 链路未更换，未增加意图规则或启用分类器。整体目标继续进行。
