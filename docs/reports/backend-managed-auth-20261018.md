# 认证服务故障与业务异常分别处理

日期：2026-10-18。基线：`5113e5eeebd0d4db3201fc124703ca2af8881130`。

沿托管 API Key 的签发、存储查询、认证、权限依赖和安全中间件审查，复现两层异常混淆：`AccessControlManager.authenticate` 把数据库故障改成 `AuthenticationError`；中间件认证 `try` 又包含后续业务执行，导致已认证业务的异常被改成 401 或 429。管理器缺失也被解释成凭据无效。

删除管理器的宽泛捕获及异常重分类，让原始服务错误向调用边界传播。中间件仅捕获认证阶段错误，认证成功后在 `else` 中执行下游业务；真实凭据错误保持 401，认证限流保持 429，认证服务故障返回明确 503。业务异常和取消保持原对象，交给业务错误处理。异常类型依赖改为正常模块导入，避免导入失败时异常处理名称尚未绑定；同时删除一个原有未使用导入。**生产代码净减少 2 行**，没有新增运行时检查或回退。

使用真实签发的隔离密钥和独立 SQLite 数据库，前后核对 **12 个场景**。有效、错误、吊销、限流及取消行为保持一致；数据库错误在管理器中保留原对象，认证存储或管理器不可用返回 503；业务运行错误、业务自身的认证／限流异常均不再被中间件改写。故障响应不暴露密钥或内部错误正文。

扩展现有管理器回归以核对原始数据库异常，增加三个真实接口回归，覆盖存储故障、管理器缺失和业务错误。只运行 6 个相关模块与核心集成安全测试类，**56 项通过，无失败或跳过**。语法树核对其他权限实现、中间件及构造逻辑保持原样；静态错误、语法及差异格式检查通过。未重跑全量回归，未调用付费模型。

按服务器修改与验证、部署、本地内容核对同步的顺序推进。部署后就绪和前端登录页均为 200，匿名受保护接口为 401，配置及前端进程保持不变。
