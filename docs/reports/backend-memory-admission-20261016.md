# 记忆任务未受理不得标记为完成（2026-10-16）

## 实际缺陷

投递确认后的记忆任务使用持久回执独立完成。服务器原代码在隔离 SQLite 中沿真实调度器、complete_turn 和 DeliveryMemoryWorker 复现：全局语义记忆容量已满，正常授权偏好的原文已 recorded，但调度器未受理任务、模型调用为零；拒收原因 capacity 被压成 skipped，持久回执据此标为 completed。数据库只重新选取 pending/running，因此容量释放、重新确认投递或重启均不会补做该任务。closed 拒收存在同一问题。

这不是正常空记忆或明确的业务跳过，而是必要步骤没有开始。Web 的回写反馈此前也未识别这两种未受理状态。

## 根因修复

调度器在唯一拒收记录点为 capacity/closed 保留真实状态，状态快照与最近回执一致；禁写、非用户来源及未启用等正常业务跳过继续为 skipped。complete_turn 已同步传递本次拒收状态，持久 worker 已有 pending 分支直接生效，无需增加状态映射、重试层或并行任务。

聊天的既有保存提示机制识别未受理状态，明确本次回复不证明结构化记忆已写入；仅在原文确实 recorded 时提示原文已保存。保存失败、删除栅栏和来源冲突的提示优先级保留。此次只修改两个生产文件，没有改动队列容量、模型、分类器、权限、投递所有权和租约协议。

交互删除使用 schedule_and_wait，保留既有 not_scheduled 回执；投递路径明确延迟操作并通过 schedule 执行，不需要修改这一独立契约。没有对历史已误标完成的真实回执进行猜测重放。
