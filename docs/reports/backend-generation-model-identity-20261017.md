# 回复模型标识只依赖本轮提供商

基线：`2ac20f689b16841c92a55b6cbab10e4dcf86ae9e`。

## 问题与修改

本地提供商的回复生成后，原代码调用管理器的全部提供商状态，再从嵌套字典中选择本轮模型；缺失标识时用 `Unknown` 组成成功响应。隔离故障注入复现：未使用提供商的状态错误会阻断已生成的回复，选中提供商缺少标识则会以 `Unknown` 成功返回。

`backend/api/generate.py` 现在只读取请求中已确定的提供商实例；云模型继续使用本轮绑定的快照，不改用当前全局选择。模型名称必须是非空字符串，读取失败或缺失时不伪造名称，以明确的 503 和 `model_status` 阶段报错，指出模型已调用但消息尚未保存。原始失败原因通过异常链保留，客户端和日志不输出原异常文本。

最终生成未调用模型的结果，即原有 `modelInvoked=False` 分支，跳过生成后的模型标识读取，继续使用原有结果标签及保存语义。必需的响应缓存身份读取不在本阶段调整。生成失败计数、失败调用记录、消息保存与角色记忆流程仍走原有处理；没有为简化错误代码绕过失败审计。

业务源码增加 23 行、删除 6 行，净增 17 行，无新依赖或意图规则。现有 LoRA 隔离装配函数只补充真实管理器原本具有的提供商字典项，未修改业务断言。

## 验证与范围

32 项定向检查首轮全部通过：14 项新增检查覆盖三个本地提供商的无关状态故障隔离、缺失/非法名称、原始原因和失败审计、确定性结果、生成后全局选择变化和绑定云快照；18 项现有检查覆盖本地适配器目录、显式及激活选择、原有确定性结果与请求快照/计数器一致性。没有重复全量回归或调用真实模型。

通过 Python 3.10 语法解析、差异空白和 Ruff E9/F 增量检查。AST 对比确认除标识读取及对应错误分类之外，生成、审计、持久化和记忆实现未改动；旧测试只补齐装配数据，原断言保持一致。

通过只读 SQL 读取当前模型配置，再用实际云提供商的显式配置快照核对名称有效性；没有查询 API 密钥、初始化数据库单例、创建 HTTP 客户端或请求模型。服务更新后就绪及前端登录页面返回 200；匿名受保护接口返回 401，安全响应头正常；运行配置和其他服务进程不变。

故障证据来自隔离注入，不表示生产环境曾发生这些故障；本阶段没有进行真实本地模型推理或新的 DeepSeek 回答质量验证。全局提供商切换的整体事务和同步机制不在本次变更中。整体优化继续进行。
