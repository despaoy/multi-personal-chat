# 退出清理错误传播与精简

原有资源关闭辅助函数和各后台模块的关闭捕获会吞掉异常，随后仍记录清理完成；异步 Redis 关闭也会忽略客户端及池的异常。本阶段让这些外层清理错误明确传播。

- 使用标准库退出栈替换重复的关闭捕获，保持任务、调度器、数据库及客户端的依赖顺序。一个关闭失败后仍尝试其余资源，最后清除生命周期引用。
- 使用退出上下文保留多个关闭错误及原始启动/请求错误的异常链。普通回调在连续失败时可能丢失前一个异常，本阶段的失败测试定位并修复了该问题。
- 关闭目标延迟至实际执行时解析，覆盖后台任务排空期间才首次创建的模型实例，同时保持没有模型时不新建实例。该遗漏经完整隔离用例复现后修正。
- 同步资源继续在线程中关闭；未创建的模型管理器保持不创建，模块关闭回调延迟导入。只有清理成功才记录完成，错误日志只记录资源标签和异常类型。
- Redis 客户端和池通过直接的 `try/finally` 都尝试释放，错误不再被忽略；清除已退出生命周期的客户端、池和异步锁引用。
- 删除一个只检查 `finally` 代码结构的旧测试，相关行为已有启动失败、请求异常、正常退出和取消场景覆盖；其余既有测试及断言未改。

阶段有效覆盖 32 个场景。首次 30 项中 29 项通过，发现一个连续关闭错误丢链问题；修复后仅运行失败、新增及直接受修改影响的 19 项，全部通过。最后复核模型释放时机，新增隔离复现并在修正后仅运行 8 项相关检查，全部通过。其余有效结果保留，未重复全量测试，真实模型调用为 0。静态检查无新增问题，语法保持 Python 3.10 兼容，生产代码净减少 39 行。

服务器先修改、定向验证和部署，再对新版本执行真实关闭并恢复启动。管理器 PID 对应启动器，实际应用为子进程；首次日志采样过早且主应用 INFO 标记未启用，不能据此判断关闭失败。随后依据实际应用子进程的完整退出事件确认正常退出，没有为日志采样问题再次重启。最后的延迟目标修正部署后，另行等待实际子进程退出及完整日志，确认 `Application shutdown complete`、进程结束及没有关闭错误。只带回布尔及计数摘要。

恢复后的后端就绪、前端登录页均为 200，匿名保护接口为 401，安全响应头正常；配置和其他服务未改变。随后同步本地及 GitHub。

范围限制：本阶段修复外层生命周期及 Redis 释放路径，未承诺各后台子系统内部已经没有独立错误捕获。启动业务、异步去重客户端发布、模型、记忆和检索策略保持原样，总体优化目标继续进行。
