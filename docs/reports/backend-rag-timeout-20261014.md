# 检索限时准备明确失败与协程顺序修复（2026-10-14）

## 实际问题与修改

检查当前语义规划 → 检索限时选择 → 检索 → 证据审核 → 回答生成链路，发现 _rag_retrieval_timeout 将运行时初始化/状态读取异常吞掉，返回常规限时继续。调用方还在 asyncio.wait_for 的参数求值中先创建 _retrieve_rag_bundle 协程，再计算限时；若限时准备失败，协程可能未等待。

删除选择器的宽泛 catch/pass，初始化和状态读取异常直接传播到已有检索/证据审核 503 边界，保留原异常原因。先计算 retrieval_timeout，再构造和等待检索协程；准备失败时没有新检索工作或回答调用。冷启动继续使用 max(常规限时, 冷启动限时)，热状态继续常规限时，不放宽预算、不禁用索引、不更换检索方案或模型。

生产 api/generate.py 净减少 2 行。没有增加错误包装层、依赖或关键词规则；正常空检索、显式关闭检索和语义规划仍保留原行为。

## 定向验证

服务器 9 项直接相关控制通过（1.10 秒），未重跑已通过集合或全量回归。覆盖热状态、正常冷启动和常规限时更长时的限时选择；初始化和状态读取故障均保留原异常。两项链路故障控制使用完整原始输入和实际语义规划解析，以明确的录制规划结果说明 unresolved_source 与 control；原请求尚未给出出处是测试前提，目标是验证运行时故障停止，不把缺少来源当产品缺陷。

故障时断言 HTTP 503、原异常链、检索工厂未调用、回答未调用，证明不会先构造协程再失败，也不把故障伪装为无匹配。正常空检索控制检查先准备限时，再创建/执行检索，随后由明确的测试模型表达来源未知；显式关闭检索仍不初始化索引。所有生成和规划都是声明的单元控制，付费模型调用 0，不作为新的 DeepSeek 回答质量结论。

语法、增量静态和差异检查通过，无新增问题。部署仅重启后端，核对就绪响应、配置哈希及其他服务进程，随后同步本地和 GitHub。未改动运行凭据、模型、生产数据库、记忆、索引或既有检索超时配置。

整体后端优化目标继续，本阶段只完成检索准备故障传播和协程顺序，不声称全项目全部降级已清除。
