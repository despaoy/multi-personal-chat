# 研究数据工作流绑定当前应用数据库

基线：`bc3bfce3a96407a49949de2b31decc284d96664b`。先审查偏好数据、历史采样、检索题库和评测入口，以及权限、客户端和相关测试，再在服务器复现和修复。

## 问题与实现

六个偏好接口和四个检索评测接口仍使用模块导入的全局数据库，管理员权限却已在当前应用数据库中复核。两个数据库不同时，列表、导出、历史采样和写入会落在错误存储；当前应用存储故障也可能被另一个数据库的成功响应掩盖。

十个入口统一复用已有 `get_request_database` 依赖，直接向注入的数据库提交原有操作。删除四个重复 SQL 转发函数和两处全局数据库导入。生产代码净增 17 行，用于明确依赖参数及调用排版，没有新增判断分支、错误类型或数据库回退。

原有业务、SQL、分页、过滤、创建、更新、删除和评测计算保持不变；归一数据库变量及调用方式后，业务函数 AST 一致。直接调用接口函数的测试显式传入已有存储，HTTP 测试提供完整应用容器，保留原有有效断言。

## 验证

- 原生 SQLite 和真实 JWT 下执行完整十个入口，包含创建、审核更新、导出、历史采样、评测及删除。修改前，十次权限复核读取当前应用，但十二次业务数据库操作全部落在全局库；修改后，业务操作全部归属当前应用，全局访问为零。
- 在删除测试新记录之前核对两种记录的实际归属，确认偏好对和检索题只创建在正确库；历史与评测问题也来自该应用。这里的十二次操作不包含十次管理员角色复核。
- 四个读取/采样/写入故障场景从错误的 200 成功变为明确的 500。匿名访问仍为 401，已被数据库降权的旧管理员令牌仍为 403。
- 应用库与全局库相同的对照场景，完整响应 SHA-256 保持 `4c0e9edae362046ccd063bb3f8326d130dd1bb735ddfef64528d4a01d389e1a2`。
- 在独立 PostgreSQL 测试库中经原生适配器、相同鉴权和完整十个入口再验证，业务访问为当前库十二次、全局零次；四个故障均明确返回 500。完整正确响应与 SQLite 一致，适配器正常释放。
- 只运行四个相关测试模块，55 项全部通过；新增四项覆盖双应用完整流程、读取和插入故障及权限边界，没有重跑全量回归。
- 语法、未定义/重复/未用名称检查及服务器仓库完整性检查通过。服务器启用后，后端就绪和前端登录页为 200，匿名受保护接口为 401 并保留 `nosniff`，配置和前端进程不变。

本阶段只验证研究数据的数据库归属。检索返回值为明确的测试控制，不作为检索语义质量或向量索引归属的证据；模型调用为 0，没有修改真实用户数据或运行配置。
