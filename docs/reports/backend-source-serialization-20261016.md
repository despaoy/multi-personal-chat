# 删除延后来源预算中的无用序列化

日期：2026-10-16。基线：`2e944df0dc7b3d5ecd0356cbbaafb0f28896f387`。

实际云模型链启用延后来源预算：SourceMemoryService.recall 在完整来源超过初步字符上限时，保留同一批刚核验授权的来源，用 compile_sources(max_chars=None, max_items=None) 生成完整候选包，再由最终请求预算决定是否接纳。旧编译器即使没有字符上限，也会逐条序列化全部累计前缀，丢掉这些中间结果，最后再序列化完整包，造成无用的二次增长处理量。

现在只在有字符上限、确实需要检查时生成 candidate 前缀包；无上限路径仅生成最终完整包。顺便把已经位于 if self._defer_budget 内部的 max_items 三元式改成恒定 None。没有增加缓存、策略、配置或模型调用；有上限时仍检查完整转义后长度，不截断原话，不用较短旧来源替代放不下的新来源。新鲜授权读取、来源顺序和来源归属语义不变。

服务器隔离观察真实 compile_sources：6 条时序列化 7→1 次，累计参与序列化的记录数 27→6；100 条时 101→1 次，累计记录数 5150→100。直接编译与真实 SourceMemoryService 延后预算路径分别验证，后者复用现有完整 repository 测试边界。两种规模在修改前后均与独立构造的完整 JSON 字节、顺序和诊断一致；只对自然变化的 elapsed_ms 检查有限非负。实际 fresh 读仍分别一次、批次大小 6/100，第一遍有上限拒绝仍只检查完整首条。观察器只替换目标模块的 JSON 引用，最后恢复，不修改全局 JSON，不把重复加工减少声称为某个延迟加速比例。

现有 4 项定向行为检查通过（0.43 秒）：完整六条延后来源、不以较短来源替代；固定来源数及显式 compiler cap；真实 SQLite 记录经授权重读仅保留完整候选且不伪造事实；末尾否定不截断且不换旧来源。没有新增镜像单测，也没有重复全量回归。
