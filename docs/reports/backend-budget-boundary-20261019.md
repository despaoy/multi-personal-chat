# 预算错误与实际模型调用的边界

基线：`21fde2b53309d7b89dcea584d0fc962ca2f36c24`。

## 问题与修复

审查生成编排、上下文预算、提供方适配、熔断、普通/SSE 接口和失败审计后，复现了实际问题：连续 5 次完整输入预算超限时，提供方调用次数为零，模型熔断器却被打开，随后正常请求也无法完成。

- 将既有 `InputBudgetError` 从角色证据选择器移至公共预算模块，20 处导入指向统一归属；保留 `ValueError`、错误参数和原异常链契约，没有创建另一套异常类型。
- 熔断范围从整个检索/编译流程收敛到实际提供方调用。预算拒绝不再消耗模型熔断状态或计入模型故障指标；真实提供方错误、开放拒绝和恢复探测继续受保护。
- 预算错误提供统一且不包含用户原文的公开原因。普通接口返回明确的 503，SSE 以明确错误事件终止，不返回成功或缓存结果。
- 保留失败尝试审计。`model_invocations` 表包含前置失败尝试，不能据其行数声称已经调用模型；真实提供方调用次数在对照中独立记录。
- 流式服务创建、迭代和关闭归属同一消费作用域，使用标准库 `aclosing`，删除手工关闭分支及重复作用域。服务初始化失败也能正确返回错误事件并释放上下文。

生产代码增加 16 行，删除一处重复错误日志。没有新增语义规则、重试、依赖、框架或熔断器实现；模型请求参数及调用内容不变。

## 验证

服务器先修改和验证，再同步本地。

- 真实编译器、隔离 SQLite、注册表和实际 API 的对照中：修复前 5 次预算失败使熔断器开放、正常请求被拒；修复后 5 次失败均明确报告预算不足，没有调用提供方或创建模型熔断状态，随后正常请求完成并调用提供方一次。
- 普通知识问答由笼统 500 改为明确预算错误；流式由笼统内部错误改为预算错误。失败路径不调用提供方、不缓存，也不发送 `done`。
- 原有真实提供方故障的受控测试仍确认：5 次实际失败打开熔断，下一次拒绝保留原原因，恢复探测和取消释放正常。
- 第一批 44 项检查中 36 项通过、8 项发现上阶段流式入口的双重作用域问题。修复后仅补跑失败项及直接关联检查，共 13 项通过；合并后 48 项唯一检查全部通过，没有重复运行此前 121 项预算检查或整体回归。
- 新增 4 项行为检查。所有旧断言保持不变；仅导入归属变化的函数通过 AST 比较确认逻辑不变。模型调用参数 AST、熔断基础设施源码、静态检查和仓库完整性检查通过。
- 部署后后端就绪和前端登录为 200，受保护接口为 401 并保留 `nosniff`。配置和其他服务进程未变。

全部提供方输出均为明确的受控合成边界，真实模型费用为零，不作为新增 DeepSeek 质量验证。原始探针有一次 `AskRequest` 类型使用错误，仅修正并补跑未完成的 API 观察，已经完成的熔断对照没有重测。
