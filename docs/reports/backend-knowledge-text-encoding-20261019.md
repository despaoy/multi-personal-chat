# 知识导入原文与文本格式统一

基线：`3d90fc661920a7e218a7670599012427291ae6bc`。范围为 ZIP、扫描目录及其子目录的文本导入，以及对应前端入口。

## 问题与修改

三个导入分支分别猜测编码，目录的文本读取还会转换换行。UTF-8 编码标记被保留在正文中，UTF-32 内容可能被当作 UTF-16 存储；ZIP 的文件大小计算与目录不一致。同一来源因入口不同，可能形成不同的 RAG 原文。

现在共用一个严格解码函数：文件有 Unicode 编码标记时遵从标记；无标记时使用明确选择的格式，默认为 UTF-8，旧版中文可选择 GBK。删除依次尝试多种编码的回退。三个入口均保留正文换行，文件大小按原始字节计算。无法解码的条目报告具体格式错误，沿用既有的 complete/partial/failed/unconfirmed 完成状态、权限、路径及索引更新边界。

前端增加共享的格式选择控件，并将选择传递到两种导入接口。目录扫描失败不再由 Hook 返回空数组；页面显示错误并关闭扫描窗口，避免把服务故障展示成“没有目录”。生产代码共净增加 21 行，其中后端净减少 1 行；没有增加服务层、重试或语义规则。

## 验证

- 88 项相关测试首次全部通过，包含新增的 24 项导入契约检查；原有测试函数和断言保持不变，只有公共请求辅助函数支持格式参数与重试目录。
- 真实 SQLite 与 ASGI 的 21 组隔离观察：修改前 16 组写入，其中仅 3 组正文完全一致；修改后 15 组应接受的输入全部保留准确正文和原始文件大小，其余 6 组明确失败。GBK 默认失败后可通过显式选择完成导入，混合文件保留部分完成状态。
- 执行实际 TypeScript API 方法、Hook 及两种格式控件的服务端渲染，确认格式参数传递、扫描异常传播和加载状态释放。使用受控请求，不连接外部服务。
- 全项目 TypeScript 检查、三个修改文件的 ESLint 检查、Next.js 生产构建通过；Python 基础静态检查、差异检查与服务器仓库完整性检查通过。
- 部署后后端就绪和前端登录页面均返回 200，受保护接口返回 401 并保留 nosniff；配置文件摘要及其他服务进程保持不变。

## 影响与限制

无标记的 GBK 文件需要显式选择“旧版中文”；现有已存储文档没有重写。编码标记作为格式元数据消耗，不写入正文。此阶段没有修改模型提示或调用配置，没有付费模型调用，没有重复运行完整回归，也没有验证 PostgreSQL 或进行登录后的浏览器视觉检查。其他知识库读取 Hook 的错误处理不在本阶段修改范围内。
