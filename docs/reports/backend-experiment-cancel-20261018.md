# 实验取消后确认线程结束与记录终态

基线：`8b6245be3f195127c9c7cf4f60bd31324080e6ab`。审查实验创建、计算与最终写入、共享执行器和应用关闭顺序，再用原生数据库、真实 JWT、HTTP 任务取消和完整冻结合成资料复现时序。

## 问题与实现

原来的线程卸载在请求取消后停止等待，工作线程仍继续执行。第一条检索受阻时取消，后台仍执行完八次检索，记录永久保持 running。三种实验在创建写入尚未结束时取消，也会在请求结束后写出 running 记录。最终提交期间取消则可能已实际完成，不能统一覆盖成失败。

- 将线程执行归属集中到 `services/experiment_execution.py`。调用方确认同一个工作任务完成后才释放请求；重复取消只等待原任务，不重新执行底层工作。意外工作错误保留在取消异常的原因链中。
- RAG 实验器持有自己的取消信号，并在下一检索轮次前检查，当前同步操作完成后停止剩余检索。
- 创建阶段和计算阶段的取消统一写入 failed、`error=cancelled`，显式保留请求的 mock 模式。终态更新在一个条件 SQL 中仅作用于 running 记录，已完成提交保持 completed。
- 收尾写入失败继续抛出真实错误，保留取消上下文；工作函数原始取消异常对象也保持不变。

生产代码净增 62 行，用于上述实际取消行为。没有新增错误类、重试、任务框架或配置项。除取消处理和已知模式参数传递之外，API 业务与 RAG 算法的 AST 对照一致，正常响应保持不变。
