# 记忆查询分词收敛为每请求一次

基线：`5f3dd7bedfe94469f8a302d9bcd35d3bb9dcb1fb`。

## 问题与修改

沿记忆候选读取、查询扩展、语义/词面排序、证据构建和上下文消费链路审查后，确认候选评分循环反复计算相同查询的 bigram。事件候选还会为相同查询再计算一次；加载较长用户话题上下文时，这些重复计算随候选数量增长。

将查询视图转换为不可变 bigram 集合放到候选循环之前，每个视图只加工一次，候选内容和事件主题复用这些集合。没有改变相关度公式、扩展内容、排序策略或结果结构，也没有增加共享缓存、依赖、异常处理或语义规则。生产代码行数不变，其余代码不变。

## 测量与验证

服务器先修改和验证，再同步本地。

- 真实隔离 SQLite 中存放 64 条完整、带来源编号和证据的候选，其中 16 条含事件主题；使用 9028 字的完整合成用户话题上下文。
- 8 组对照覆盖普通/上下文召回、语义通道开启/关闭、查询扩展开启/关闭。语义向量使用明确的受控提供器，不代表真实模型质量评估。
- 同一查询在每组中的分词次数从 80 次降为 1 次；4 组长上下文查询合计从 320 次降为 4 次。完整选中 `MemoryItem`、候选数和除耗时外的诊断结果摘要全部不变；原始存储及向量调用次数不变。
- 该合成负载中，长上下文分词片段耗时由约 146–149 毫秒降至约 2.5–3.1 毫秒。这是计算片段的观测值，不是 HTTP 延迟承诺。
- 9 项相关既有测试首次通过，覆盖旧记忆召回、查询扩展、消融、证据、语义门控和向量缓存。没有新增或修改测试。
- Python 静态检查、仓库完整性和差异格式检查通过。部署后后端就绪和前端登录为 200，受保护接口为 401 并保留 `nosniff`；配置和其他服务进程未变。

未改变 SQL，未进行付费模型调用、真实语义质量验收或重复整体回归。
