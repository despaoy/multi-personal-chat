# 知识库创建区分真实重名与存储故障

基线：`30a101bf63dc4539824e08fae12ac356e9c7c71f`。审查创建 API、SQLite/PostgreSQL 数据层、重复创建后文档发布和目录导入的调用链。

SQLite 的知识库和文件夹创建捕获所有 IntegrityError 后返回 None；PostgreSQL 捕获所有异常，再按异常文字是否包含 unique/duplicate 决定返回 None。API 将 None 解释为名称已存在，因此非重名的实际写入故障会被错误报告为 409。

四个创建方法现在通过数据库已有的指定唯一约束执行 ON CONFLICT DO NOTHING：知识库名称全局唯一，目录名称在对应知识库内唯一。只有正常冲突返回 None。SQLite 其他失败回滚并保留异常；PostgreSQL 由会话事务统一提交与回滚，删除异常文本猜测和手动异常分支。生产代码净减少 20 行，没有新增服务层、重试或配置，也没有修改表结构。

验证结果：

- 21 项定向测试首次全部通过，包含新增的 5 项存储故障、恢复、并发和目录作用域检查，以及直接关联的重复创建事务和批处理导入检查。原有测试与断言没有修改。
- 在新建隔离 SQLite 和 PostgreSQL 数据库中，按两种对象共完成 4 组实际 ASGI/数据库观察，每组检查合法创建、真正重名、原描述不被覆盖、故障回滚、恢复写入和并发唯一创建。
- 使用完整合法请求，由真实数据库触发器制造非唯一约束的存储故障，并让 PostgreSQL 异常文本包含 duplicate。改前四条路径均错误返回 409、底层没有抛出错误；改后隔离 API 返回 500、底层保留 IntegrityError/DBAPIError。真正重名仍为 409，并发请求仍只创建一条。
- 静态、差异和服务器仓库完整性检查通过；非目标数据库方法与定义经 AST 核对不变。部署后就绪、登录均为 200，受保护接口为 401/nosniff，配置和其他服务进程不变。

没有故障注入业务数据库、迁移历史数据、调用模型或重复完整回归。隔离 PostgreSQL 首次观察结束时，脚本误用了 SQLite 资源关闭方法；修正后在全新测试数据库取得有效改前记录，没有把该脚本问题当作产品故障。此阶段没有重建前端；HTTP 故障状态来自隔离 ASGI 对照，线上仅做正常健康与权限检查。
