# 长期记忆 M1：规则写入保真

本轮只改规则记忆的提取与写入，未增加模型调用、图数据库或迁移。后台 LLM 记忆开关及原有路径保留。

## 已实现

| 用户表达 | 当前行为 |
| --- | --- |
| 我来自成都。我现在住在上海。 | 分别保存来源地与现居地，不互相覆盖 |
| 我喜欢咖啡，但晚上不喝。 | 保存完整句子和条件，不只留下“喜欢咖啡” |
| 我喜欢喝咖啡。随后说我不喜欢咖啡。 | 在同一用户、角色、会话范围内替代旧版本，保留历史和来源 |
| 我叫小明？ | 不当成姓名事实 |
| 我喜欢读小说。 | 不再仅因“小说”二字拒绝记忆 |
| 明天我会去面试。 | 保留“明天”原文，不推断绝对日期或完成状态 |

流程：用户消息 → 拒绝记忆/敏感信息/虚构语境门禁 → 按句排除问题与不确定陈述 → 小范围字段提取 → 保留原句与条件 → 查找同范围同键记录 → 重复忽略、明确更新版本、不明确冲突存候选。

普通规则写入复用现有 append-only 存储。保留 evidence、source_message_ids、observed_at 和版本关联。valid_from 表示本次记录当前陈述的时间，不代表推断出的真实事件起始时间。置信值仅为规则元数据，不是校准后的正确率。

饮品别名仅支持咖啡、红茶、绿茶、奶茶、牛奶、茶及其“喝”前缀，不进行任意动词删除。旧数据不批量重写；遇到唯一匹配的旧别名时沿其版本链更新。SQLite 使用事务、PostgreSQL 使用已有键级事务锁核对当前版本，防止过期写入覆盖较新版本；竞争时最多重读三次，不调用模型。

## 候选不是已确认事实

多个旧别名同时有效，或新旧条件不同而无法判断是补充还是更正时，保留旧有效记忆，把新句存为 pending；候选不进入默认有效记忆读取。相同候选重复出现不反复追加。它不会自动调用模型或弹出强制复核。现有管理接口可读取候选，但本轮未新增候选审核界面或自动转正机制。`new_memories` 统计新增存储记录，也包括候选，不等于新增已确认事实。

## 边界与下一步

- 仍是规则系统，不具备完整否定、转述、条件逻辑理解。保守门禁可能漏记复杂句、历史经历和带引号的普通表达。
- 跨消息“但晚上不喝”还不能自动接到之前的偏好；不同条件不会自动合并。
- 不批量修复旧 `user_location`，因为旧字段无法可靠判断来自何处还是住在哪里。
- 暂未实现 M2 事件结束/状态流转、相对时间解析，也未实现 M3 候选召回调整。
- 超长句整体跳过，避免截断后丢失否定或条件。应通过后续真实对话样例评估漏记率。

## 参考与验证

借鉴 [LongMemEval](https://arxiv.org/abs/2410.10813) 对更新、时间与拒答的区分、[Mem0](https://arxiv.org/abs/2504.19413) 的记忆更新思路，以及 [Zep](https://arxiv.org/abs/2501.13956) 的来源与时间记录思路；这是轻量工程适配，不是复现论文系统或其性能。

新增回归覆盖误提取、条件保留、版本更新、重复、旧别名、并发、范围隔离和真实聊天完成入口。测试只用临时 SQLite，不修改真实用户数据库；PostgreSQL 分支未经过真实服务集成测试。自动测试通过不代表自然对话质量已获得模型实测提升。
