# 完整记忆来源的访问与删除契约（r108已接通受控回答读取，默认关闭）

## 为什么需要完整来源

r104真实轮岗输入包含“到月底结束”，模型只保存了“我目前在唐山轮岗”和“之后回苏州”两个证据片段。排序修复能找回已有片段，却无法重建没保存的限定语。源语句与模型候选必须分离，模型裁决失败/漏提取不能被解释成用户从没说过。

## 为什么不能直接给每条claim复制整个原话

r105在独立临时SQLite用现有仓储模拟这种**尚未实现**的设计，得到两个反例：

1. 同一句产生姓名和住址两个同级claim，把整句复制进两条metadata。ERASE住址只删除该claim及其派生后代，姓名行里的整句副本仍含住址。
2. 姓名claim被允许保存为user_global时，其metadata里的整句也能跨会话/角色读到，附带了原本不应随姓名扩大范围的其他信息。

证据：`.tmp/mechanism-r105-source-copy-audit/result.json`。这是候选设计风险审计，不表示生产代码已经加入这个字段或已经发生此类泄露。SQLite和PG的现有ERASE都沿parent/supersedes关系删派生链，并不识别独立同级记录的源文本副本。

## 实现必须满足的要求

- **独立来源身份。** 来源属于具体用户、角色和原始会话/分支，不能只凭可能重复的source_message_id做全局关联。只用可验证的原始范围，不推断缺失归属。
- **不随事实扩大权限。** user_character/user_global事实的授权不自动涵盖整条原话。原始会话上下文只能在该来源被授权的范围读取。
- **片段与完整来源分开。** claim保留自己的证据片段；完整来源作为来源引用显示，不改写成当前事实。说话者为用户不等于句中所有实体都是用户，不能给整段套上已确认user事实标签。
- **来源不要四处复制。** 优先复用现有消息来源或单独的来源实体，批量按被选候选关联读取；避免每个claim复制整句、扫描全部历史或新增复核模型。
- **删除联动。** ERASE/单条删除/清空必须同步撤销能再次呈现目标内容的完整来源引用，且不误删其他独立已保存事实。旧引用失效后，不得用兜底读取原始聊天重新恢复它。原聊天记录本身是否删除属于另一条明确接口，不能擅自删聊天。
- **并发不能复活。** 同源候选写入、排队补全与删除交错时，后到的旧工作不能重建已撤销的来源可见性。必须验证实际事务边界，不能只依赖内存检查或新的字符串指纹。
- **不截掉晚到的否定或条件。** 预算容不下整段时不得把前缀当完整来源；应保留片段标志并暴露未纳入原因。
- **在线开销有界。** 来源关联应批量、范围受限；引用展示标签不进入向量/词面相关性，沿用r104检索与展示分离。

## 验证清单

覆盖同句多个事实、条件后置、取消/改期、第三方转述、scope扩大、跨用户/角色/分支同名source ID、单条删除与ERASE/清空、派生关系、并发迟到写入、预算不足、仅源语句无有效模型候选。SQLite与PG必须有对应语义证据；新来源功能尚未实现，不以本契约或现有时间字段测试宣称完成。

## r106实施边界

新增独立memory_sources、memory_source_links、memory_source_fences。来源身份是原始六元范围加source_message_id，不是内容指纹。版本化claim在同一事务保存当前消息的来源关联；user_global/user_character规范化之前记录原始范围。没有从模型历史source IDs推断原会话，也没有迁移/复制既有聊天。

capture_memory_source/list_memory_sources是内部数据库能力，尚未接入scheduler、召回、编译或HTTP接口。支持无claim来源记录和有界批量读取，原话不可被同ID重试覆盖。narrative显式拒绝，等待可核验的分支授权，不能把未支持当已验证隔离。旧add_or_update兼容槽尚不创建来源关联，启用前需处理这一边界，不能靠回读聊天补全。

ERASE/单条删除在事务内撤销所删claim及派生claim关联的完整来源；独立同级事实和不相关来源保留。清空会话同时撤销该精确会话的无claim来源。撤销后仅保留来源身份、空body/observed_at和revoked状态，不保留删除理由或事实文本；这不是物理磁盘擦除保证。原始聊天不变。每用户一条删除时间水位防止删除前已接收但尚未入库的任务补写原话；SQLite写事务/PG行锁保证跨进程时序。比较使用固定精度UTC，等于水位也保守拒绝，因此同一系统时钟粒度内的相邻任务可能被拒绝。仅阻止旧来源恢复，不宣称已解决所有旧claim任务重新写事实的问题。

**运行检索前尚有重要缺口：** 未提取成claim的另一条来源可能重复包含已删除事实，却没有关联ID。仅沿关联删除不能证明这条无关联原话已不含目标；旧兼容写入也有同类问题。必须明确“删除后旧未关联来源不可重新用于回忆”的读取/失效策略及其召回代价，再开启全量来源兜底。不能把本轮关联删除测试包装成所有原话遗忘语义都已解决。

后续还需接入可信接收时刻的保存门控（沿用拒绝存储/非用户来源策略）、处理无候选及无效目标的保存、预算完整性/可见省略原因、source quote与fact主体分离、来源检索/展示分离，并进行真实模型对照。当前新增存储不影响生成提示词，不新增模型调用，不代表真实回答已经变好。

## r107更新（以上r106段落是历史边界，不再代表当前全部状态）

1. `MemoryEnrichmentScheduler`已在模型判断之前经repository捕获完整原话，沿用schedule现有非用户/opt-out/敏感信息门控和可信job.observed_at。原话不按模型输入长度截断。明确遗忘请求自身不进入原话池；无source_message_id/不支持的原始scope不会猜身份，保留原有语义写入但记录缺失原因。空/格式错误/无效操作候选/模型调用失败仍保留已准入原话；关联事实仍按原有规则验证，不放行错误target。

2. 删除后的来源读取采用**原话层时间边界**：同一platform/adapter/sender在已授权ERASE成功或clear后，所有此前完整来源不再进入list/batch读取，包括无claim及仅与其他claim关联的重复原话。SQL在同一快照按owner主键读取水位，列表可走scope/state/time范围索引，batch仍走最多200个精确主键。独立结构化事实不受这项原话读取过滤影响。代价是其他角色/会话中该用户的旧原话细节也暂时不可召回，不能声称选择性遗忘无损；新收到的话可继续保存。已关联来源仍清除body/observed_at；未关联旧来源只是撤销可读性，物理文本仍在表中，不能宣称磁盘擦除/全部副本物理销毁。

3. 测试复现“capture完成→模型等待→clear→模型返回ADD”仍能恢复claim。版本化append现于SQLite/PG既有owner事务锁下比较可信observed_at和删除水位，迟到结果抛明确撤销异常，scheduler计为skipped而非服务故障。不新增复核查询/模型调用，复用已有锁和水位。只有带时区可信接收时刻的现代写入有此保证；未知/naive旧时间不猜时区，旧add_or_update事实写入仍非完整并发遗忘认证。

4. 9组11份r104真实生成结果已通过实际scheduler和SQLite重放，完整来源11/11保留；服务器新鲜Qwen3-8B无LoRA四次写入也保存4/4完整来源。没有进行来源→回答读取，本轮结果只证明保存与事务路径，不能声称自然度/人物模拟或答案正确性已经改善。

下一阶段需实现有界来源候选检索、预算完整性和不可信来源数据包（说话者不等于句中主体），再接入实际生成做对照。没有claim的来源仍需明确可执行的删除入口；错误/不存在target的事实ERASE不能冒称已删除某段原话。缓存与并发读取需遵守读取时间边界，不能用旧缓存绕过SQL或回读聊天恢复。该扩展尚未开启回答读取，未经生产部署。
